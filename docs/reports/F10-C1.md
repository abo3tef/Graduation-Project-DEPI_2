### Ordering, filters, pagination (task items T2, T3)
- **Ordering contract:** `OccurredAt` desc → `Type` ascending in true ordinal order (`Diagnosis` < `MedicalNote` < `Medication` < `Visit`) → `Id` ascending in canonical GUID string order. Deterministic and stable across pages.
- **OccurredAt conventions:** Visit = `VisitDate`; Diagnosis = midnight UTC of `DiagnosisDate` (`DateOnly` has no time-of-day); Medication = parent visit's `VisitDate` (a prescription item has no date; EF joins `m.Visit.VisitDate`); Note = `CreatedAtUtc`.
- **Filters:** `eventType` canonicalized case-insensitively (validator rejects unknown spellings first); `from`/`to` as instants for visit/medication/note sources, and **UTC calendar days** for diagnoses (`DateOnly.FromDateTime(from.UtcDateTime)`).
- **Pagination at the data source:** 4 filtered SQL `COUNT`s produce the accurate `TotalCount`; when `skip >= totalCount` an empty page is returned without fetching; otherwise each source fetches at most its top `skip + pageSize` rows (SQL-ordered, column-projected, `AsNoTracking`) and the ≤ 4·(skip+pageSize) merged rows are ordered/paged in CLR. **No portable single SQL union exists** (`DateOnly` vs `DateTimeOffset` columns); the bounded-prefix design keeps the in-memory set O(pageSize) per source, never the whole timeline (AGENTS §3.1). The correctness invariant — each source's top-K equals its prefix in the global order because the type is constant within a source — is documented in the service remarks and exercised by the paging tests.

## Review follow-up (2026-11-15, same cycle, uncommitted)

After the architecture review approved the design, three fixes were required and applied
(no authorization, migration, or architecture changes):

1. **Pagination overflow (required):** `pageNumber` is only bounded from below, so
   `(pageNumber - 1) * pageSize` in int arithmetic wrapped for huge page numbers (e.g.
   `pageNumber=int.MaxValue` produced a negative OFFSET — a real SQL error on MySQL). The
   caller now computes `skip` with `long` arithmetic, runs the four source queries in two
   passes (counts only, then a bounded fetch only when `skip < totalCount`), clamps the
   per-source fetch window to `min(skip + pageSize, totalCount)`, and pages the merge with the
   safe `int`. Beyond-last pages — including `int.MaxValue` — return `200` with an empty
   `items` array and correct metadata. Regression tests: Application
   (`Extreme_page_number_returns_an_empty_page_with_correct_metadata`) and WebAPI
   (`Timeline_huge_page_number_returns_200_with_empty_items_and_correct_metadata`).
2. **Ordering contract correction (required):** the previously documented type tie-break chain
   (`Diagnosis` < `Medication` < `MedicalNote` < `Visit`) was not the actual
   `StringComparer.Ordinal` order. The true order is `Diagnosis` < `MedicalNote` <
   `Medication` < `Visit`; the API contract, this report, and the service remarks now state
   the implemented order. Regression test:
   `Note_sorts_before_medication_at_the_same_instant` (note audit-stamped at the same instant
   as a visit and its medication → `MedicalNote` < `Medication` < `Visit`).
3. **GUID tie-break hardening:** the SQL sources order ties by the `char(36)` id column
   (canonical GUID string order on MySQL) while the CLR merge compared `Guid` values (signed
   little-endian byte order) — the two diverge for GUIDs whose first group crosses the signed
   int boundary (`7fffffff…` vs `80000000…`: string order puts `7f` first, .NET Guid order
   puts `80` first), which could mis-select a page when more rows than the fetch limit fully
   tie within one source. The merge now ties on `Id.ToString()` with `StringComparer.Ordinal`,
   matching the SQL column order without any client-side materialization before `Take`.
   Regression test: `Medication_tie_breaks_in_canonical_guid_string_order` (that exact id
   pair; the test fails under a Guid-order tie-break).

Observed results after the fixes: `dotnet build Medilog.sln` — 0 warnings / 0 errors;
`dotnet test Medilog.sln` — **Application 247/247, WebAPI 119/119** (test counts in the
commands table above reflect the pre-fix state). Real MySQL execution remains **unverified**
(no reachable instance) — this applies to the overflow path, the two-pass query shape, and the

### Review round 3 — count-only guard verification

A reviewer reported that `QueryDiagnosisEventsAsync`, `QueryMedicationEventsAsync`, and
`QueryNoteEventsAsync` were missing the `take <= 0` count-only guard that
`QueryVisitEventsAsync` has. Inspection of the current source disproved the finding: all four
helpers carry the identical guard immediately after their `CountAsync` (service lines
250, 309, 371, 432), each before any fetch expression is built. Adding duplicate guards would
be dead code, so the service was not changed.

Because the guards are behaviorally invisible on InMemory (a `LIMIT 0` fetch returns the same
empty rows), the verification was made structural instead: a query-counting test-support
interceptor (`IQueryExpressionInterceptor`) was wired into `MedicalRecordScenario` via an
optional `countQueries` constructor flag, and the new test
`Count_only_pass_runs_no_fetch_queries` asserts that a `pageNumber = int.MaxValue` timeline
request compiles **exactly 4** queries — the four source counts — and nothing else (8 would
mean a guard is missing). The test passes.
