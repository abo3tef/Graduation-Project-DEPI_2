## Delivered

### Types (`types/payment.types.ts`)
- `Payment` now matches `PaymentResponse`: added `patientId`, `doctorId`; `paidAt: string | null`; `notes: string | null`.
- `PaymentAppointmentOption` matches `PayableAppointmentResponse` (`id`, `patientId`, `patientName`, `doctorId`, `appointmentDate`, `startTime`).
- `PAYABLE_APPOINTMENTS_LIMIT = 50` (the API default; the API max is 100).
- `PAYMENT_FORM_FIELDS`, `PaymentFormErrorKey`, `CreatePaymentFormErrors` for the form's field-error contract.
- UI enums stay lower-case (`pending|partial|paid`, `cash|card`) — see deviation D1.

### Boundary (`services/payment-enums.ts`, `services/payment-readers.ts`)
- PascalCase ⇄ lower-case label maps plus type guards. The API serializes enums via `JsonStringEnumConverter`, so `"Cash"`/`"Paid"` are the only accepted wire values; the wrong casing is rejected, not coerced.
- `readPayment`, `readPaymentPage` (delegates to the shared `readPagedResult`), `readPayableAppointments` are the single place untrusted JSON becomes typed data. Missing/mistyped fields raise the shared `invalid-response` error instead of leaking half-typed objects into the UI.

### API service (`services/payments.service.ts`) — mock file deleted
- `listPayments(filters, signal)` → `GET /api/payments` with `search,status,method,pageNumber,pageSize`; empty search and `all` filters are omitted, enums sent in API casing.
- `listPayableAppointments(signal)` → `GET /api/payments/payable-appointments?limit=50`.
- `createPayment(input)` → `POST /api/payments` (`Pending` by contract). When the user ticked "mark as fully paid now", it then calls `PUT /api/payments/{id}/status` with `{status: "Paid"}`.
- `updatePaymentStatus({id, status})` → `PUT /api/payments/{id}/status`.
- New `PaymentPartiallyRecordedError` + `isPaymentPartiallyRecordedError`: the POST succeeded but the follow-up status call failed. It carries the created `Pending` payment and the original cause so the UI can say the payment exists without claiming it is paid.
- `payments.mock.ts` deleted; no mock data remains in payment code.

### Hooks (`hooks/usePayments.ts`)
- `usePayments(filters)` (keeps previous page data while refetching), `usePayableAppointments(enabled)`, `useCreatePayment`, `useUpdatePaymentStatus`.
- Retry is limited to one attempt and only for network/5xx failures; `4xx` (401/403/404/409/validation) is never retried.
- Success toasts distinguish `created` / `createdPaid` / `statusUpdated`; failure toasts show a translated message, with a dedicated `partiallyRecorded` warning.
- `usePaymentErrorMessage()` maps any failure to a `Payments.errors` key.
- Query keys are `['payments', ...]`; every mutation invalidates `paymentKeys.all` (list + payable picker).

### Error mapping (`services/payment-errors.ts`)
- API `code` wins over HTTP status: `payment.not_found`, `payment.appointment_not_found`, `payment.already_exists`, `payment.invalid_status_transition`, `payment.paid_final`, `payment.invalid_amount`, `payment.invalid_method`, `payment.notes_too_long`, `payment.missing_reference`, `identity.invalid`, `validation.failed`.
- Falls back to `network` / `invalidResponse` / `unauthorized` / `forbidden` / `notFound` / `conflict` / `server` / `unknown` by status; server English text is never displayed.
- `mapPaymentFieldErrors` maps FluentValidation codes (`NotEmpty`, `NotNull`, `MaximumLength`, `Predicate`, `Enum`) onto the form's own message keys so 400 responses land on the right field.

### Rules (`utils/payment-rules.ts`)
- `nextStatuses` encodes exactly the API transitions: `pending → partial|paid`, `partial → paid`, `paid → []`.
- `validatePaymentForm` mirrors the server's shape rules (appointment required, amount parsed and range-checked, method in the allow-list, notes length) for fast feedback only.

### Components
- `PaymentFormDialog.tsx`: appointment picker fed by `payable-appointments` (no manual GUID entry), amount, method, notes with a live counter, and the "mark as fully paid now" checkbox. The fields component is only mounted while the dialog is open, so each opening starts clean without a state-resetting effect. Handles loading, picker-error (with retry), "no payable appointments", server field errors and a form-level error; moves focus to the first invalid field.
- `PaymentStatusDialog.tsx`: shows the payment summary and offers only the statuses `nextStatuses` allows; the inner form is keyed by payment id so it never shows a stale transition. A paid payment shows the final-state message instead of a form.
- `PaymentsTable.tsx`: nullable `paidAt` renders as a dash; rows whose status cannot change show the "paid — no further changes" note instead of a status button (the API would answer `409 payment.paid_final`).
- `PaymentsPreview.tsx`: keeps its name and export so `app/[locale]/payments/page.tsx` is untouched; now renders the real list with filters, pagination, record button and both dialogs, plus loading skeleton, empty, filtered-empty and error-with-retry states.
- `utils/formatters.ts`: `formatDate`/`formatDateTime` accept `null`/`undefined` and return a dash; `formatTime` accepts both `HH:mm` and `HH:mm:ss`.

## Deviations from the task file / approved plan

1. **D1 — case boundary.** The F2 screens keep their lower-case UI enum values; one boundary module (`payment-enums.ts`) converts to and from the API's PascalCase labels. Chosen over rewriting every component to PascalCase.
2. **D2 — create flow.** `POST` always creates `Pending`, so "record as fully paid" is a checkbox that triggers a second `PUT /status`. A failure of that second call is reported as *saved as pending*, not as a failed create (approved by the owner).
3. **D3 — token.** No token handling was added inside the payments feature. The central token is F6-C2 and is not merged; the interim manual test takes the JWT from the existing medical-records dev-token panel via `registerAuthHeadersProvider`. `DevTokenPanel` was **not** modified.
4. **D4 — role-based hiding.** Payment actions are not hidden per role. The route is guarded server-side (`[Authorize(Roles = "Doctor,Secretary")]`) and the screen renders a translated `403`/`401` message. Hiding buttons per role would require the F6 auth session, which is not available yet.
5. **D5 — file naming.** `PaymentsPreview` was kept as the page component and upgraded in place rather than renaming it to `PaymentsView`, because renaming would have required editing `app/[locale]/payments/page.tsx`, which is outside this Cycle.
6. **T4 not done (excluded).** The dashboard payment widget is untouched; `totalRevenue` remains `null`. AC-2 is **not** claimed.
7. **Command path.** The task file says `cd Front_End`; the repository directory is `frontend/`, which is what was used.
8. **Amount parser.** The existing `parseAmountInput` treats both `,` and `٫` as a decimal separator, not as a thousands separator. The feature follows the existing behavior (`250,50` → 250.5); no thousands separators are accepted. A first version of the test asserted `'1,000.00' → 1000` and was corrected to the real behavior rather than changing the shared parser.
