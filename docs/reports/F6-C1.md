## Deviations from the plan

| # | Deviation | Reason |
|---|---|---|
| 1 | `JwtOptions`, `SeedOptions`, `EmailOptions`, `AuthLinkOptions`, `AuthTokenLifetimes` and `FirebaseOptions` are bound manually from `IConfiguration` factories instead of `AddOptions<T>().Bind(...)` | `Microsoft.Extensions.Options.ConfigurationExtensions` is not referenced by the Application/Infrastructure projects; binding by hand keeps D-41 (no new package) and behaves identically |
| 2 | `Microsoft.IdentityModel.JsonWebTokens` declared in no project file | It resolves transitively at 8.14.0 (Infrastructure) while WebAPI runs 8.19.2 from `JwtBearer`; F6-C1 uses only APIs present in both, so no package was added (D-41) |
| 3 | Account→response mapping is explicit construction, no AutoMapper profile for the auth feature | The auth responses carry security-sensitive fields; mapping an entity automatically risks exposing the hash or state. T10 asked for AutoMapper "where mapping is needed" — here it is not |
| 4 | Password-reset requests that fail validation do not consume the token | A rejected request must not burn the user's only link |
| 5 | `reset-password` does not verify the email address | Verification stays the only path that activates an account (Q-11); a reset link proves mailbox control but was not approved to change account state |
| 6 | A pre-existing time-dependent test was corrected (`ClaimsContractTests`) | The signature test asserted `IsValid` for a token issued at a fixed 2026-11-14 timestamp with a 24-hour lifetime, so it started failing on the next day; it now skips lifetime validation, which the dedicated expiry test still covers |

No scope expansion: no refresh token, no MFA/SMS, no admin screens, no frontend, no removal of the
development header identity or `DevTokenPanel` (already assigned to F6-C2 / F11-C2, D-42).
