## 1. Trigger

Phase 0 left the two merged feature lines with two different list envelopes and two different
error bodies:

- **F1 (appointments):** `PagedResult<T>` used `pageNumber` in the response, a default page size of
  20 and a maximum of 100; validation errors were camelCase with `errorCodes`.
- **F4 (medical records):** no list endpoint, but validation errors kept FluentValidation's
  PascalCase property names and threw `FluentValidation.ValidationException`.
- Framework-generated errors (unmatched route, `401` challenge, `405`, `415`) had no body or used
  MVC's default `ProblemDetails`, which lacks `code` and `traceId`.

Q-04 was answered on 2026-11-13 and fixes the contract. Phase 1 applies it once, in both layers.

## 2. What changed

### P1-C1 — Backend paging contract

- `Common/Paging/PagingDefaults.cs`: `MinPageNumber = 1`, `DefaultPageNumber = 1`,
  `DefaultPageSize = 10`, `MaxPageSize = 50`. Features no longer declare their own limits.
- `Common/Paging/PagedResult.cs`: `Items`, `Page`, `PageSize`, `TotalCount` and a computed
  `TotalPages = ceil(TotalCount / PageSize)` (`0` when there are no rows).
- New `Common/Paging/IPagedQuery.cs` (the shared request surface) and
  `Common/Paging/PagedQueryValidator.cs<T>` (the shared `pageNumber`/`pageSize` rules, so each
  feature validator only adds its own filters).
- `ListAppointmentsQuery` implements `IPagedQuery`; `ListAppointmentsQueryValidator` derives from
  `PagedQueryValidator<ListAppointmentsQuery>`.
- `AppointmentService` list path keeps ordering `appointmentDate, startTime, id` (stable
  tie-breaker) and applies paging at the data source.
- New `backend/tests/Medilog.Application.Tests/Paging/PagingContractTests.cs` pins the JSON
  property names (`page`, `pageSize`, `totalCount`, `totalPages`) and the `TotalPages` ceiling.
  `ValidatorTests` and `AppointmentsEndpointTests` updated (`page` in the response,
  `pageSize=51` → `400`, default-size case, deterministic tie-breaker case).

### P1-C2 — Backend error envelope

- `ErrorCodes` gained `request.invalid`, `auth.unauthorized`, `request.method_not_allowed`,
  `request.unsupported_media_type` and `appointment.mismatch`.
- New `Common/Validation/RequestValidation.cs`: one `ValidateAsync` helper that runs a
  FluentValidation validator and throws `RequestValidationException` (top-level code
  `validation.failed`, per-field `FieldErrorCodes`).
  `AppointmentService` and `MedicalVisitService` (all six F4 validators plus the
  appointment/patient mismatch path) now use it; `FluentValidation.ValidationException` is no
  longer thrown by application code.
- New `WebAPI/Common/ApiProblem.cs`: one builder/writer for the canonical envelope (`type`,
  `title`, `status`, `instance`, `code`, `traceId`, optional `detail`, and camelCase
  `errors`/`errorCodes` for validation). Field keys are normalized (`$.status` → `status`,
  `PatientId` → `patientId`). It also maps a status code to a default code/title and exposes
  `ToResult` for MVC paths.
- `WebAPI/Common/GlobalExceptionHandler.cs` rewritten on top of `ApiProblem`
  (`FluentValidation.ValidationException` is kept only as a safety net).
- `Program.cs`:
  - `InvalidModelStateResponseFactory` returns the same envelope with `request.invalid`.
  - `ApiBehaviorOptions.SuppressMapClientErrors = true`, so MVC client errors such as `415` stay
    body-less and the status-code middleware emits the canonical envelope.
  - `UseStatusCodePages` runs right after `UseExceptionHandler`, so framework-generated `401`,
    `404`, `405`, `415` and body-less `5xx` responses carry `code` and `traceId` too.
- F4 tests updated to `RequestValidationException`, `Errors.Keys`, camelCase keys,
  `validation.failed` and `errorCodes`; new
  `backend/tests/Medilog.WebAPI.Tests/ErrorEnvelopeTests.cs` covers `400` (validation and
  binding), `401`, `403`, `404`, `405`, `409`, `415` and `500` end-to-end.

### P1-C3 — API contract documentation

- New `backend/docs/api/CONVENTIONS.md`: the shared source of truth for JSON/transport rules,
  list/filter/pagination (request `pageNumber`, response `page`, 10/50), deterministic ordering,
  success status codes, the error envelope with examples, and the error-code catalogue.
- `backend/docs/api/appointments.md`: `page`/`pageSize` updated to the shared contract, the
  temporary-contract note removed, the error section replaced with the canonical envelope and the
  new codes.
- `backend/docs/api/MEDICAL_RECORDS_API.md`: camelCase validation example with
  `code`/`errorCodes`/`traceId`, other-failure code table, and the Q-04 wording corrected (the
  contract is defined; F4 still has no list route).

### P1-C4 — Frontend shared contract

- New `frontend/src/types/paging.ts`: `PagedResult<T>` (`page`) plus `DEFAULT_PAGE_SIZE = 10` and
  `MAX_PAGE_SIZE = 50`.
- New `frontend/src/lib/api/paging.ts` (`readPagedResult(value, readItem)`) exported from
  `lib/api/index.ts`, with `paging.test.ts` covering the envelope, empty page, unknown members and
  malformed input. This is now the single boundary reader for list responses.
- Appointments: the local `PagedResult` and page-size constants were removed;
  `appointment-readers.ts` uses `readPagedResult`; `AppointmentsPage.tsx` renders `page.page`;
  hooks import the shared constants. Tests updated (`test-utils.tsx` `page`, readers,
  `AppointmentsPage`, `BookingForm` day query `pageSize=50`).
- Payments (still a mock, F2 backend blocked by Q-01): `payment.types.ts` and
  `payments.service.ts` use the shared type and constants; `totalPages` is now
  `ceil(totalCount / pageSize)` and `0` when empty, and the page is clamped to `1` in that case, so
  the mock matches the API contract it will replace.

## 4. Deviations / notes

- **Request/response asymmetry is intentional** (Q-04): the query parameter is `pageNumber`, the
  response member is `page`. Documented in `CONVENTIONS.md` so it is not "fixed" later.
- **`MaxPageSize` 100 → 50** truncates the F1 day-schedule helper
  (`useAppointments` → `MAX_PAGE_SIZE`) to 50 rows for one doctor/day. There is no pagination loop
  for that screen. At 50 appointments per doctor per day this is unlikely, but it is a real
  limitation and is recorded here rather than silently hidden.
- **F2 is still a mock.** Only the paging shape was aligned; no payment rule, status, method or
  attribution was invented (Q-01 remains open).
- **No new list endpoint** was added. F4 still has no visit list route, and F5 has no dashboard
  route; `CONVENTIONS.md` §7 states that explicitly.
- `ValidationException` (FluentValidation) remains mapped in `GlobalExceptionHandler` as a safety
  net for any code path that still throws it; application code no longer does.
- The `500` body remains generic; the exception is logged server-side with the same `traceId`.
