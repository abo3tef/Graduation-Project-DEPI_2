## Deviations from the plan

1. **Diagnosis ordering is configured with `ForCtorParam`, not `ForMember`.** `MedicalVisitResponse`
   is a positional record, so AutoMapper builds it through its constructor parameters; a
   `ForMember(... MapFrom(...))` on `Diagnoses` was silently ignored and the test proved the
   returned list kept insertion order. `ForCtorParam(nameof(MedicalVisitResponse.Diagnoses), …)`
   is the configuration that actually applies to a record. Covered by a regression test.
2. **Text normalization moved into the mapping profile.** `MedicalRecordText.Normalize` is applied
   in the explicit `MapFrom` for `ChiefComplaint`/`Symptoms`/`ClinicalNotes` (and `Description`),
   and `DiagnosisName` is trimmed there. The service no longer re-assigns the same members after
   mapping, so the rule is declared once (AGENTS §3.3, no duplicated logic).
3. **The create-visit map also ignores `PatientId`.** The plan listed `Id`/`DoctorId` only; ignoring
   `PatientId` as well guarantees no identifier reaches an entity from client input. The service
   assigns `patient.Id` after the ownership check.
4. **`.ToList()` was removed from the ordering expression.** It did not fix the record issue; the
   `ForCtorParam` change did, and element mapping is performed by AutoMapper.
5. **`Microsoft.EntityFrameworkCore.Relational` 10.0.14 pinned in the test project.** Referencing
   Infrastructure (EF Core 10.0.14) and the MySQL provider (Relational 10.0.12) together produced an
   MSB3277 version-conflict warning, which would break AC-10 (0 warnings). The explicit 10.0.14
   reference unifies the version. Test-project only; no production package changed.

No other deviation from the approved C2a scope.

## Deviations from the plan

1. **`CreatedAtRoute` with a named route instead of `CreatedAtAction`.** The first test run proved
   that `CreatedAtAction(nameof(GetVisitAsync), …)` throws
   `InvalidOperationException: No route matches the supplied values` — MVC suppresses the `Async`
   suffix in action names by default, so the supplied action name did not exist. The GET action now
   has `Name = "MedicalVisits.GetVisit"` and both `POST` actions use `CreatedAtRoute`. This was a
   real defect caught by the integration tests, not a test-only workaround.
2. **The exception handler serializes the runtime `ProblemDetails` type explicitly.** Serializing
   through `IProblemDetailsService` uses the declared `ProblemDetails` type, which can drop the
   derived `ValidationProblemDetails.Errors`; the handler writes the runtime type so the root
   `errors` member is part of the contract. A test asserts it.
3. **The development token command uses `--name "<doctor-guid>"`, not
   `--claim "sub=<doctor-guid>"`.** Decoding a generated token showed that `--claim sub=…` produces
   `"sub": ["<user name>", "<guid>"]`; inbound mapping then yields two name-identifier claims and
   the first one is not a GUID. `--name` writes a single `sub` value, which is exactly the `sub`
   claim D-16 requires.
4. **`appsettings.Development.json` is not committed with auth values.** `dotnet user-jwts create`
   writes the non-secret issuer/audience there on demand; the file is left untouched so the
   repository carries no environment-specific auth configuration. The signing key stays in user
   secrets.
5. **The test factory removes every `IDbContextOptionsConfiguration<MedilogDbContext>` registration
   before adding InMemory.** EF Core 10 records each `AddDbContext` options action in that service;
   removing only the context/options descriptors would leave the MySQL action to run and throw the
   missing-connection-string error.
