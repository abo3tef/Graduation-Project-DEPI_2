## Deviations from the plan

1. **Diagnosis ordering is configured with `ForCtorParam`, not `ForMember`.** `MedicalVisitResponse`
   is a positional record, so AutoMapper builds it through its constructor parameters; a
   `ForMember(... MapFrom(...))` on `Diagnoses` was silently ignored and the test proved the
   returned list kept insertion order. `ForCtorParam(nameof(MedicalVisitResponse.Diagnoses), …)`
   is the configuration that actually applies to a record. Covered by a regression test.
2. **Text normalization moved into the mapping profile.** `MedicalRecordText.Normalize` is applied
   in the explicit `MapFrom` for `ChiefComplaint`/`Symptoms`/`ClinicalNotes` (and `Description`),
   and `DiagnosisName` is trimmed there. The service no longer re-assigns the same members after
   mapping, so the rule is declared once (AGENTS §3.3, no duplicated logic).
3. **The create-visit map also ignores `PatientId`.** The plan listed `Id`/`DoctorId` only; ignoring
   `PatientId` as well guarantees no identifier reaches an entity from client input. The service
   assigns `patient.Id` after the ownership check.
4. **`.ToList()` was removed from the ordering expression.** It did not fix the record issue; the
   `ForCtorParam` change did, and element mapping is performed by AutoMapper.
5. **`Microsoft.EntityFrameworkCore.Relational` 10.0.14 pinned in the test project.** Referencing
   Infrastructure (EF Core 10.0.14) and the MySQL provider (Relational 10.0.12) together produced an
   MSB3277 version-conflict warning, which would break AC-10 (0 warnings). The explicit 10.0.14
   reference unifies the version. Test-project only; no production package changed.

No other deviation from the approved C2a scope.

## Remaining risks and blockers

1. **C2b is blocked** on Q-07 (no authentication scheme registered, so `[Authorize]` cannot work)
   and Q-02 (`Patient.DoctorId` is nullable; the single-owner workspace rule is an assumption).
   `ICurrentUser` has no implementation, so `IMedicalVisitService` cannot be resolved in the
   running API yet — it is registered but not reachable through any endpoint.
2. **InMemory is not MySQL.** The unique `appointment_id` index and the composite foreign keys are
   not enforced by the test provider, so those guarantees rest on the explicit application checks
   and on the EF configuration until a MySQL-backed test exists.
3. **No concurrency token** on `MedicalVisit`/`Diagnosis`: concurrent `PUT` is last-write-wins.
4. **No audit columns** on `MedicalVisit`/`Diagnosis` (inherited `BaseEntity`): “who changed what”
   is not recorded.
5. **Q-08 (clinical notes)** still decides whether `ClinicalNotes` stays in the contract.
6. **No real MySQL verification.** Model/snapshot agreement only; the local instance rejects the
   configured credentials.
7. **SRS/BRD texts are still absent** from `docs/`, so the rule IDs referenced in the plan remain
   inferred.
