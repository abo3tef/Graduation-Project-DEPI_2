# Execution Report — F4v2-C2 (Diagnosis Delete: Frontend)

- **Date / Contributor / AI tool used:** 2026-11-16 / Mohamed Shalaby / OpenCode
- **Branch:** `feature/shalaby-auth`
- **Cycle:** F4v2-C2 — Diagnosis delete frontend. Plan approved 2026-11-16
  (`docs/tasks/F4-v2/F4v2-C2.md`, decision D-23).
- **Goal:** let the doctor who owns the visit delete a diagnosis entered by mistake from the visit
  screen, behind an accessible confirmation dialog, with the list refreshed from the server and
  clear success/error feedback.

## Delivered

- `features/medical-records/api.ts`: `deleteDiagnosis(visitId, diagnosisId): Promise<void>` calling
  `DELETE /api/medical-visits/{visitId}/diagnoses/{diagnosisId}` through the shared `requestVoid`
  transport (mirrors `deleteMedication`).
- `features/medical-records/hooks/use-diagnosis-mutations.ts`: `DeleteVariables` and
  `useDeleteDiagnosisMutation(visitId)`. On success it invalidates only
  `medicalRecordKeys.visit(visitId)` and shows `diagnosisDeleted`; on error it shows
  `diagnosisDeleteFailed`. No optimistic removal and no rollback path (D-23).
- `features/medical-records/components/DiagnosisSection.tsx`: a `Delete` button per row next to
  `Edit`, opening the reused `ConfirmDeleteDialog`. The row is removed only after the mutation
  succeeds; on success the dialog closes and focus lands on `#diagnoses-add` (the deleted row no
  longer exists, so the dialog's own focus restore has nothing to focus). Cancel resets the
  mutation and closes the dialog without touching the list.
- `messages/en.json` / `messages/ar.json`: `MedicalRecords.diagnosis.{deleteAction, deleteTitle,
  deleteDescription, deleteConfirm, deleting}` and
  `MedicalRecords.notifications.{diagnosisDeleted, diagnosisDeleteFailed}` (RTL-safe Arabic).
- `features/medical-records/api.test.ts`: the feature's first automated test — `deleteDiagnosis`
  request shape (URL, `DELETE`, `204` → `void`) and the `404` → `ApiError not-found` mapping.

## Behaviour verified

- **Delete path:** `Delete` → dialog (focus on Cancel, `Esc` closes when idle, "cannot be undone"
  copy) → `Delete permanently` → `204` → visit query invalidated → row disappears on refetch +
  success toast. No optimistic state.
- **Cancel path:** resets the mutation, closes the dialog, list unchanged.
- **Error path:** `403/404/network/server` keep the dialog open with the shared `MutationAlert`
  plus the error toast; the list is unchanged. `401` is handled by the existing F6 central
  handler (session cleared → `/login?reason=expired`), with no new code here.
- **Authorization:** the section only renders inside `MedicalRecords`, which is wrapped in
  `RequireRole(['Doctor'])` (UX only). The backend `DELETE` enforces role and ownership (C1);
  a secretary or foreign doctor cannot delete even by calling the API directly.
