# F8-C2 — Patient Management & Search: Frontend & Integration

- Feature: F8   - Owner: Menna   - Branch: `feature/menna-patients`   - Phase: Phase 2
- Status: Approved
- Depends on: F8-C1, F6-C2 (central token)

## Goal
Patient list/create/edit/delete screens and a reusable patient picker that replaces manual GUID entry in the appointment (F1) and visit (F4) forms.

## Source requirements
FR-08, FR-09, FR-10, FR-12, FR-40, FR-41, FR-49; NFR-10/11; AGENTS.md §3.1, §6.5.

## Business rules & security constraints
Doctor sees full patient form; secretary sees only basic fields (UX mirror of the backend rule); delete requires confirmation and shows the 409 reason; picker never exposes data beyond the lookup DTO.

## Affected layers & files
`features/patients/` (api, components incl. `PatientSelect`, hooks, types, `index.ts`); routes under `app/[locale]/…/patients`; **minimal edits** to the F1 appointment form and F4 visit form to use `PatientSelect` imported through the feature barrel (coordinate with their owners); `messages/ar.json` + `en.json`.

## API contract
As frozen in F8-C1.

## Common rules for this Cycle (AGENTS.md is authoritative)
- Existing structure only (`app`, `components`, `features`, `data`, `i18n`, `messages`, `types`); feature code in `features/<name>/` with a barrel `index.ts`; no `src/`.
- Native `fetch` through the single shared API client + TanStack Query (queries/mutations, cache invalidation); no Axios; no new libraries without approval.
- Strict TypeScript, no `any`; loading / empty / error / success states; accessible forms; all text via next-intl with matching keys in `messages/ar.json` and `messages/en.json`; RTL/LTR safe layout.
- Frontend guards are UX only; the backend remains the enforcement point.
- Checks to run and report: `cd Front_End && npm run lint && npm run build`, plus a manual test with the seeded `Admin`, `Doctor`, `Secretary` users.
- Done = AGENTS.md §11 + Execution Report (`docs/reports/<CycleId>.md`) + proposed STATE.md update.
