# F7-C1 — Payments: Backend

- Feature: F7 — Payments Backend & Integration   - Owner: Habiba   - Branch: `feature/habiba-payments`   - Phase: Phase 2
- Status: Approved
- Depends on: F6-C1 checkpoint A (roles), Phase 1 F1/F2 (appointments, payment screens)

## Goal
Complete payment endpoints (create, list/search with pagination, update status) with JWT authorization and doctor-scoped data.

## Source requirements
No payment requirement exists in SRS/BRD/Class Spec (GAP closed by the instructor's F2/F5 scope and the team). Related: BRULE-10 (secretary restrictions), FR-44/FR-47 (appointment status), FR-39 (dashboard). Payment rules come from the model in STATE.md §8 (Q-21).

## Business rules & security constraints
Secretary manages payments only for assigned doctors (per the approved scoping, Q-09); doctor reads only their own payments; no medical data in payment DTOs; client cannot set ownership, recorder, or payment state fields directly (AutoMapper must not map them); money as decimal with explicit precision; no rule invented beyond the documented model.

## Affected layers & files
Domain: existing payment entity (verify). Application: payment service, DTOs, validators, mapping profile. Infrastructure: payment configuration/precision/indexes (+ migration only if the model changes). Api: payments controller.

## API contract
`POST /api/payments` · `GET /api/payments` (search, filters, pagination, stable sort) · `PUT /api/payments/{id}/status` *(route per existing contract; confirm in plan)* · optional `GET /api/payments/{id}`. Filters from the existing Phase 1 contract style (doctor, patient, appointment, status, date range, search).

- [ ] Secretary can create/list/update status within allowed doctors; doctor sees only own payments; unauthenticated → 401, wrong role → 403.

- [ ] Pagination metadata and total count are correct; sorting is stable.
- [ ] Dashboard total matches the sum of persisted payments for that doctor.

## Common rules for this Cycle (AGENTS.md is authoritative)
- Pattern: MVC Controller (thin) → plain Application service → `IApplicationDbContext`; no MediatR, no extra repository. EF Core Code First; one `IEntityTypeConfiguration<T>` per persisted entity; migration reviewed and merged in the order set in STATE.md §4.
- FluentValidation for every request; AutoMapper profile for DTO mapping; never expose entities; reuse the existing Phase 1 pagination/filter contract (do not create another).
- Role and ownership come from the validated JWT, never from client input; secretary never reaches medical data.
- Checks to run and report (only those that exist): `cd Back_End && dotnet restore && dotnet build Medilog.slnx && dotnet test Medilog.slnx`.
- Done = AGENTS.md §11 + Execution Report (`docs/reports/<CycleId>.md`) + proposed STATE.md update.
