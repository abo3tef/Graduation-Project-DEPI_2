## 1. Goal

Give an authenticated, active doctor two read-only use cases for **their own patients**, enforced on the server:

1. **Medical Profile** — current patient information (all Class Spec §4.2 attributes), allergies, chronic conditions.
2. **Medical History** — the patient's previous visits, each with its linked diagnoses, medications, vital signs, visit-linked notes and visit-linked lab results, newest first, paged.

**Out of scope:** controllers/routes/OpenAPI (next F3 cycle), frontend, authentication itself (Q-07), Medical Timeline and MedicalDocuments and unlinked notes/labs (F3-C2, D-11), any write operation (F4), payments, dashboard.

## 2. Applicable requirements and rules

Source: `Smart_Medical_Records_Platform_Class_Specification(1).pdf` (repo root; the SRS/BRD FR texts are not in the repository — the spec only references FR numbers).

- §4.1/§4.2: the doctor accesses only patients in their own workspace (FR-13, BRULE-04); `Patient.viewProfile()`; `Patient.getTimeline()` (deferred, D-11).
- §4.2: Patient attributes — `patientId, doctorId (owning doctor, nullable), fullName, dateOfBirth (age derived), gender, phone, address, bloodType, emergencyContact, createdAt`.
- §4.3: `MedicalVisit.getPreviousVisits()`; BRULE-06. §4.4: `Diagnosis.getHistoryByPatient()`. §4.5/§4.8/§4.9: `getHistory()`.
- §4.6: allergies displayed prominently in the profile (FR-23) — returned first-class in the profile response.
- §4.9/§4.10: `LaboratoryResult.visitId` and `MedicalNote.visitId` are optional; rows without a visit are deferred (D-11).
- BRULE-01, BRULE-05, BRULE-10: only doctors access records; every event belongs to a patient; a secretary never reads medical data.
- AGENTS §3.1 (pagination, deterministic ordering, bounded page size), §3.2 (FluentValidation), §3.3 (mapping), §4.1 (layers), §4.4 (no EF entities, no unnecessary sensitive data), §5 (server-side enforcement, doctor data scope), §7 (tests).
- `STATE.md` F3 row: view patient medical data, previous visits, diagnoses and prescriptions, medical history, medical-profile screens (screens in a later cycle).

- `ix_medical_visits_patient_id_visit_date` supports the history ordering.

- F1 patterns present and reused: `ICurrentUser` (+ dev-only `HeaderCurrentUser`), `UserRole {Doctor, Secretary}`, `NotFoundException`/`ForbiddenException`/`RequestValidationException`, `ErrorCodes`, `PagedResult`/`PagingDefaults` (20/100), `IClinicClock.LocalNow`, Application-owned store port implemented in `Infrastructure/Persistence/<Feature>`, FluentValidation 12.2.0 and AutoMapper 16.3.0 centrally registered, no MediatR. `IAppointmentService` is registered in `AddApplication` on `main` (the WebAPI host provides `ICurrentUser`), so `IMedicalRecordService` follows the same registration.

## 4. Design

### 4.1 Use cases (take `CancellationToken`; derive the actor only from `ICurrentUser`)

- `GetMedicalProfileAsync(GetMedicalProfileRequest)` — request record `(Guid PatientId)`.
- `GetMedicalHistoryAsync(GetMedicalHistoryRequest)` — request record `(Guid PatientId, int PageNumber, int PageSize)`.

Neither accepts a doctor id, role or owner id from the client.

### 4.2 Authorization order (both use cases)

1. `Role != Doctor` → `ForbiddenException` (`medical.access_denied`). **No store call is made.**
2. `UserId == Guid.Empty` → `ForbiddenException` (`identity.invalid`).
3. Validate the request (shape only).
4. Doctor missing or inactive → `ForbiddenException` (`identity.invalid`).
5. Patient missing, `DoctorId` is `NULL`, or `DoctorId != UserId` → `NotFoundException` (`patient.not_found`, identical message for all three).
6. Only then read data, always keyed by the verified `patientId`.

The ownership decision lives in Application so it is unit-testable without EF.

### 4.3 Profile response

`PatientId`, `FullName`, `DateOfBirth`, `Age` (derived in Application from `IClinicClock.LocalNow`, birthday-safe including Feb 29), `Gender`, `Phone`, `Address`, `BloodType`, `EmergencyContact` (D-07), `Allergies[]` (name, severity, description, notes), `ChronicConditions[]` (name, diagnosis date, status, notes). The owner doctor id is not exposed (the caller is the owner). No document data (D-11).

Ordering (D-13): allergies by severity (Severe, Moderate, Mild, none), then name, then id; conditions by status (Active, Controlled, Resolved, none), then diagnosis date newest first (nulls last), then name, then id. Collections are not paged (small per patient).

### 4.4 History response

A `PagedResult<MedicalVisitResponse>` of visits, newest first by `VisitDate` (UTC instant), tie-break id descending. "Previous" = all of the patient's visits (no date filter). Each visit carries: visit id, date, authoring `DoctorId` + `DoctorName`, chief complaint, symptoms, clinical notes, and its linked **diagnoses, medications, vital signs, visit-linked notes and visit-linked lab results** (with the note author's id and name).

Child ordering (D-13): diagnoses by date desc, name, id; medications by name, id; vital signs by id; notes by created time desc, id; labs by test date desc, name, id.

**Not included:** patient-level notes/labs (`VisitId = NULL`), documents, appointment id.

### 4.5 Store port `IMedicalRecordStore` (D-08)

- `GetDoctorAsync(doctorId)` → `(Id, IsActive)`
- `GetPatientOwnerAsync(patientId)` → `(PatientId, DoctorId?)`
- `GetProfileDataAsync(patientId)` → patient scalars + allergies + chronic conditions (children unsorted; D-13 ordering happens in the service)
- `ListVisitsAsync(patientId, pageNumber, pageSize)` → `PagedResult<MedicalVisitData>` (headers paged/ordered in SQL; children loaded per page)

Uses its own records (does not reuse F1's `ActorInfo`/`PatientInfo` inside `IAppointmentStore.cs`).

**Infrastructure rules:** `AsNoTracking` everywhere; explicit `Select` projections; no whole-graph `Include`; the visits page is filtered by `patient_id` first and children are then loaded by those visit ids (and additionally by `patient_id` where the column exists); vital signs are scoped through the visit ids (which are already patient-scoped) and cannot leak across patients; visit-linked notes/labs only (`VisitId != NULL`).

## 7. Acceptance criteria

- **AC-1.** `GetMedicalProfileAsync` and `GetMedicalHistoryAsync` exist behind `IMedicalRecordService`, free of EF/HTTP types.
- **AC-2.** The authorization order in §4.2 is enforced; a secretary never triggers a medical read.
- **AC-3.** Doctor/patient scoping follows D-01/D-05; the actor comes only from `ICurrentUser`.
- **AC-4.** The profile and history match §4.3/§4.4 including `EmergencyContact` and `BloodType`; documents and unlinked notes/labs are never returned (D-11).
- **AC-5.** Vital signs are scoped through visit → patient.
- **AC-6.** History is bounded, deterministically ordered with a tie-breaker, and returns correct totals.
- **AC-7.** Validators exist and are centrally registered; no entity is returned and no client input is mapped onto an entity.
- **AC-8.** `dotnet build backend/Medilog.sln` has 0 warnings/0 errors; `dotnet test backend/Medilog.sln` results are reported as actually observed; the EF model has no pending changes (`dotnet ef migrations has-pending-model-changes`).
- **AC-9.** No Domain, EF configuration, schema, migration, package or project change; no unrelated diff.
- **AC-10.** Store behavior against real MySQL is reported as **verified** or explicitly **not verified**.

## 8. Dependencies, risks, assumptions

- **Release dependency (recorded in `STATE.md`):** AGENTS §7 requires a test that a secretary cannot retrieve medical records through the API and a test that a doctor cannot retrieve another doctor's data. These need controllers, so they belong to the next F3 (API) cycle. **F3 must not be marked Done before they pass.** F3-C1 covers the same rules at the Application level.
- **R-1.** The store has no automated tests (no Infrastructure test project or EF test provider exists; adding either needs approval). Same accepted risk as F1.
- **R-2.** The in-memory fake could diverge from the real store.
- **R-3.** Shared files (`DependencyInjection` ×2, `ErrorCodes`) can conflict with other branches — coordinated through the Tech Lead.
- **R-4.** `Features/MedicalRecords/` is also the namespace Member 4 uses on `feature/shalaby-visits` for the write side; file and type names are disjoint (`IMedicalVisitService` etc. vs `IMedicalRecordService` etc.), so a future merge is expected to compose cleanly. Revisit at integration time (Q-10).
- **R-5.** Children per visit and profile collections are not paged (small per patient; revisitable if data volumes grow).
- **R-6.** Until F3-C2, patient-level notes/labs, documents and the timeline are visible nowhere, so F3-C1 alone is not the full specified read scope (D-11).
- **R-7.** An inactive doctor cannot read their own patients' records (D-06).
- **R-8.** Admin appears in the SRS/BRD but not in `UserRole`; it is denied by default and its access is undefined.
