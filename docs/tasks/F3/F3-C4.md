### 0.2 D-1 security verification (performed 2026-11-14, evidence)

The F1 lookup contract is **sufficient — the client-supplied `doctorId` is not trusted**:

1. `AppointmentService.SearchPatientsAsync` resolves the actor from the **server-side
   identity** (`RequireActorAsync` → `ICurrentUser.UserId`/`Role`; missing/inactive →
   `403 identity.invalid`) — `AppointmentService.cs:245-262`.
2. `CanAccessDoctorAsync` enforces that a `Doctor`-role caller may only pass
   `query.DoctorId == _currentUser.UserId`; any other doctor id → `404 doctor.not_found`
   (`AppointmentService.cs:254-257`). A secretary is restricted to assigned doctors
   (`IsDoctorAssignedAsync`). The query parameter is a scope *selector validated against
   server-derived identity*, never an authorization boundary.
3. The store filters in SQL — `Where(patient => patient.DoctorId == doctorId)`, `AsNoTracking`,
   DB-side limit — and projects **only `id`, `fullName`, `phone`** (no medical data)
   (`AppointmentStore.cs:174-198`). This is the minimum administrative information AGENTS §5
   allows.
4. The F3 frontend therefore sends the acting doctor's own `userId` (from
   `useActingIdentity`) as `doctorId`; even a manipulated call cannot expose another doctor's
   patients. Verified limits: `Limit 1..20` (default 10), `Search ≤ 100` chars
   (`Lookups.cs:20-36`).

## 1. Ground rules honored

- Doctor-only data: the screens gate on `identity.status === 'ready' && role === 'Doctor'`
  before any request (`enabled: ready && isDoctor`); the backend remains the enforcement
  boundary — frontend gating is UX, not security (AGENTS §5).
- Known vs out-of-scope patients are indistinguishable (`404 patient.not_found`); the UI must
  not reveal which patients exist (D-05).
- No invented medical data: no `PatientStatus` field (Q-03 open).
- Reuse, don't fork: `lib/api` (`apiRequest`, `readPagedResult`, `ApiError`),
  TanStack Query with actor-scoped keys + `keepPreviousData` + retry-once, `notify` toasts,
  `next-intl` namespaces, Tailwind tokens, feature-local UI primitives (F1 pattern),
  `cacheComponents: true` Suspense/awaited-params page pattern.
- Deep links to F4's visit screen (`/medical-records/visits/{visitId}`) are plain `href`s —
  no cross-feature imports.

## 3. Backend contracts consumed (all read-only)

| # | Endpoint | Used for |
|---|---|---|
| 1 | `GET /api/appointments/lookups/patients?doctorId={self}&search=&limit=` | patient finder (D-1; verified §0.2) |
| 2 | `GET /api/patients/{patientId}/medical-profile` | tab ① + ② (allergies, chronic conditions) |
| 3 | `GET /api/patients/{patientId}/medical-visits?pageNumber=&pageSize=` | tab ③ visit history, newest first |
| 4 | `GET /api/patients/{patientId}/notes?pageNumber=&pageSize=` | tab ④ (**C4b**) |
| 5 | `GET /api/patients/{patientId}/lab-results?pageNumber=&pageSize=` | tab ⑤ (**C4b**) |

Error mapping (shared envelope): `401 auth.unauthorized` → sign-in prompt state;
`403 access.forbidden` → doctor-only message; `404 patient.not_found` → not-found state
(unknown ≡ out-of-scope); `400 validation.failed` → non-sensitive form/query feedback;
network/status 0 → retry action. State handling per screen/section: loading (skeleton,
`aria-busy`), empty (explicit per-section copy — 0 records is normal), error (code-based,
non-sensitive), success (real data).

## 5. Acceptance criteria (F3-C4a)

1. A doctor opens `/patients`, searches their own patients by name/phone (min-length +
   debounce like F1's combobox), and navigates to a patient's status screen; identity gate
   renders before `ready`, and a non-doctor identity sees the gate — never data, never a
   request (`enabled: ready && role==='Doctor'`).
2. `/patients/[patientId]` shows the profile (§3.1 fields incl. `bloodType`,
   `emergencyContact`, derived `age`) and allergies + chronic conditions from tab ①/②.
3. Visit history (tab ③) is paged per Q-04 (default 10, max 50), newest first, each visit
   shows chief complaint/date/doctor and its diagnoses/medications/vital signs/notes/labs,
   and deep-links to `/medical-records/visits/{visitId}`.
4. Loading, empty, error, and success states exist for every data section; API errors map to
   specific, non-sensitive messages; unknown ≡ out-of-scope patient (404).
5. All user-facing strings live in `messages/ar.json` + `messages/en.json` (new `Patients`
   namespace only); AR RTL and EN LTR verified; no `any`; strict TypeScript.
6. Zero modifications outside the §2 file list (verified by `git diff --name-only`).
7. `npm run lint`, `npm run typecheck`, `npm run test`, `npm run build` all pass — reported
   only as actually observed; no fabricated results.

## 6. Test plan

- **Readers/guards (unit):** valid + malformed API payloads for profile/visit-list/lookup —
  malformed must throw `ApiError` (invalid response), never render partial data;
  `readPagedResult` contract incl. beyond-last-page empty items.
- **Hooks:** `enabled` false until identity `ready` and role is doctor; actor-scoped keys
  change with identity; `keepPreviousData` during paging; retry-once only for retryable
  errors.
- **Components:** finder (search, debounce, empty results, selection), status screen
  (loading skeletons → data → empty per tab → error per tab), visit deep-link href.
- **Conventions:** messages ar/en parity (existing `messages.test.ts` runs automatically);
  RTL conventions test (arrow mirroring, logical properties).
- **Manual (reported as observed):** dev server against the local stacked backend with
  `NEXT_PUBLIC_DEV_IDENTITY=true` — doctor sees own patients only; secretary identity sees
  the gate; direct navigation to another doctor's patient id shows the 404 state.
