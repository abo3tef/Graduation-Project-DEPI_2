## 1. Goal

Give the secretary working screens for the F1 workflows, in **Arabic (RTL) and English (LTR)**, on top of the F1-C3 API (`backend/docs/api/appointments.md`):

1. **List and filter** appointments (doctor, status, date range) with pagination.
2. **Book** an appointment (doctor and patient selection, date, start/end time, reason) with validation.
3. **Reschedule** (date/time only).
4. **Cancel** (mandatory reason, max 500).
5. **Update status** (Confirm, No-Show; Complete only when the identity is a Doctor).
6. A **central API layer** that attaches the temporary dev identity headers (`X-User-Id`, `X-User-Role`) in one place, so replacing it with real authentication later is a one-file change.

**Out of scope:** real login/auth (Q-07), payments, patients/doctors management screens, any medical data, an app-wide dashboard shell, the home page (`HomeLanding.tsx` is not touched).

**Backend (F1-C3) facts the UI must respect**
- Identity headers: `X-User-Id` (hyphenated GUID), `X-User-Role` (`Doctor` | `Secretary`); honored only when the server runs in Development with `Auth:AllowHeaderIdentity=true`.
- CORS allows any header from `http://localhost:3000`; error responses keep the CORS header.
- The dev launch profile `http` serves `http://localhost:5208` with no HTTPS redirect; the `https` profile redirects `5208 → 7206`, and a browser preflight fails on a redirect — the frontend must call the exact URL the server serves.
- Error bodies: ours are `application/problem+json` with camelCase `errors`; framework-level 400s use JSON-path keys (`$.status`, `request`). Server messages are English only and carry **no machine-readable code**.
- Paged list: `{items, pageNumber, pageSize, totalCount, totalPages}`; max page size 100; order is date, start time, id.

## 4. Blocking gaps found (need decisions before `build`)

### 4.1 No lookups for doctors and patients (Q-C4-01)
Booking needs a doctor and a patient, and the list filter needs a doctor — but the API has **no endpoint to list the secretary's doctors or to search patients** (and the patients/doctors features are empty). Without them the UI would have to ask the secretary to type GUIDs.

**Proposal — a small backend mini-cycle "F1-C3b" before the frontend build** (read-only, administrative data only, same scoping rules as the service):
- `GET /api/appointments/lookups/doctors` → doctors visible to the caller (a doctor: themself; a secretary: assigned doctors), active only: `{id, fullName, specialization?}`.
- `GET /api/appointments/lookups/patients?doctorId={guid}&search={text}&limit={1..20}` → patients **of that doctor** (caller must be in scope of the doctor, otherwise 404) matching name or phone: `{id, fullName, phone?}` only — no medical fields, no date of birth, no address.
- Application port methods + store queries (filtered and limited in the database) + tests + contract doc update.
- Optional, same cycle: add a stable machine-readable `code` extension to ProblemDetails (e.g., `appointment.overlap`, `appointment.doctor_unavailable`) so the UI can localize 409/400 reasons instead of showing English server text (Q-C4-06).

Alternatives: (b) wait for other members' patients/doctors features (unscheduled, blocks F1); (c) GUID entry in the UI (unacceptable for the secretary, acceptable only as a temporary dev tool).

### 4.2 No data to log in with (Q-C4-02)
The database is empty and there is no seeding or auth, so nobody has a valid `X-User-Id`. **Proposal:** a clearly synthetic SQL script `backend/docs/dev/seed-dev-data.sql` (2 doctors, 1 secretary assigned to one of them, 3–4 patients; fake names/phones; non-login placeholder password hash; fixed GUIDs documented) so the screens can be exercised locally (AGENTS §4.3: seed only safe, identified development data).

## 5. Proposed design

### 5.1 Routes (`src/app/[locale]/appointments/…`, thin server files)
| Route | Content |
|---|---|
| `/{locale}/appointments` | List + filters + pagination + row actions |
| `/{locale}/appointments/new` | Booking form (+ the doctor's schedule for the chosen day) |
| `appointments/layout.tsx` | Feature-local app bar (brand link, `ThemeToggle`, `LocaleSwitcher`, dev-identity chip). The marketing `Header` is not reused or modified. |

A detail page (`/appointments/[id]`) is **not** in this cycle: every mutation returns the updated appointment, and a dynamic segment adds `cacheComponents` complexity for little value (Q-C4-07).

### 5.2 Folder design
```

  errors.ts          ApiError { status, title, detail, fieldErrors, traceId } + guards
  query-string.ts    builds ?a=b skipping undefined/empty
  index.ts
src/features/auth/                 (existing empty skeleton)
  dev-identity/      Zustand store (persisted in localStorage) + devAuthHeadersProvider + DevIdentityDialog + useDevIdentity
src/features/appointments/
  types/appointment.types.ts      API types mirroring the contract; constants (statuses, limits)
  services/appointments.api.ts    list/book/reschedule/cancel/updateStatus/lookups via lib/api
  services/appointment-errors.ts  ApiError → AppointmentErrorCode (+ field error mapping)
  validation/appointment.validation.ts  pure validators (book, reschedule, cancel) mirroring server rules
  utils/date-time.ts              clinic-local date/time helpers (no UTC parsing of yyyy-MM-dd)
  utils/status-actions.ts         status × role → allowed actions (UI convenience only)
  hooks/useAppointments.ts        key factory, list query, mutations (notify + invalidate)
  hooks/useAppointmentFilters.ts  local filters state (like payments)
  hooks/useLookups.ts             doctors, patient search (debounced)
  components/                     AppointmentsPage, AppointmentFilters, AppointmentsTable (cards on small screens),

  index.ts                        public surface for route files (page-level components only)
src/components/ui/                 business-agnostic primitives (new): Button, Field/Input/Select/Textarea, Dialog (native <dialog>),
```

Changes to existing shared files are limited to: `app/[locale]/providers.tsx` (one line registering the dev auth-headers provider, marked `TODO (Q-07)`), `messages/*.json` (new namespace only), `features/appointments/index.ts`. **Not touched:** `HomeLanding.tsx`, marketing `Header`/`Footer`, the Payments feature or its messages.

### 5.3 API layer and the dev identity
- `apiRequest` reads the base URL from `NEXT_PUBLIC_API_BASE_URL` (required; clear startup/first-call error if missing), builds the URL and query, sends JSON, **asks `getAuthHeaders()` for headers on every call**, parses `problem+json` and the framework 400 shape into one `ApiError`, and turns network failures into `ApiError` with status `0`. No retries; React Query decides.
- **Switching to real auth later** = register a different `AuthHeadersProvider` (for example `Authorization: Bearer …`) or enable `credentials: 'include'` in this one file; no screen changes.
- Dev identity: the provider returns `X-User-Id` / `X-User-Role` from a small persisted store. It is active only when `NEXT_PUBLIC_DEV_IDENTITY=true` **and** `NODE_ENV !== 'production'` (defense in depth — the server also refuses headers outside Development). A compact "Acting as: Secretary · …a1b2" chip opens a dialog to paste the id and pick the role; optional defaults from `NEXT_PUBLIC_DEV_USER_ID` / `NEXT_PUBLIC_DEV_USER_ROLE`. Ids are not secrets; nothing is logged. When no identity is set, the screens show an explanatory empty state instead of firing requests that would return 403.

### 5.4 Screens and behavior
**List** — filters: doctor (from lookups), status (all + 5), date from/to; default `dateFrom = today` in the clinic time zone. Table on `md+`, stacked cards below. Columns: date, time range, patient (name, phone), doctor, status badge, reason; row actions by status/role. Server-side pagination (page size 10, like payments), `keepPreviousData`. States: loading skeleton, empty (with "New appointment"), error (message + retry), no identity.
**Book** — doctor select; patient combobox (search ≥ 2 chars, debounced, needs a doctor, resets when the doctor changes); date (`min` = clinic today); start and end time (both required; **no default duration** — optional quick-pick buttons 15/30/45/60 min only compute the end from the chosen start when pressed); reason (≤ 1000, counter). `DaySchedulePanel` lists the chosen doctor's active appointments that day (existing list endpoint) to help avoid conflicts. Submit → `201` → success toast → back to the list. Field errors map to inputs; 409 and 404 show a form-level alert.
**Reschedule** — dialog with date and times prefilled; same validations; 409 → alert; success toast; list refreshes.
**Cancel** — dialog with a required reason (≤ 500, counter); destructive confirm button; 400 field error maps to the textarea.
**Status** — Confirm (Scheduled → Confirmed), Mark no-show (Scheduled/Confirmed) with a confirmation dialog; **Complete is shown only when the identity role is Doctor**. Closed appointments (Completed/Cancelled/NoShow) show no actions. This matrix is a convenience; the backend remains the enforcer.
**Errors** — one mapping: status 0 → network; 400 field errors → inputs; 400 other → generic "check your input"; 403 → "not allowed / identity"; 404 → "not found or no access"; 409 → "time conflict or doctor unavailable" (becomes precise if the `code` extension is added); 5xx → generic with retry. Server English text is never shown directly.

### 5.5 RTL/LTR, accessibility, theming
- Tailwind **logical** utilities (`ms-/me-/ps-/pe-`, `text-start`, `start-/end-`) instead of left/right; direction-dependent icons use the existing `ltr:`/`rtl:` pairs; times (`HH:mm`) and phone numbers are wrapped with `dir="ltr"`/`<bdi>` so they do not reorder in Arabic.
- Dates are never built with `new Date('yyyy-MM-dd')` (UTC shift); they are parsed from parts and formatted with `next-intl` (`useFormatter`) using `timeZone: 'UTC'` on a UTC-constructed date. "Today" is computed in `Africa/Cairo` via `Intl`.
- Dialogs use the native `<dialog>` (`showModal`): built-in focus trap and Escape; labelled; focus returns to the trigger. Inputs have visible `<label>`s, `aria-invalid`, `aria-describedby` for errors; the first invalid field is focused on submit; status badges carry text (not color alone) with theme-aware colors following the payments badge pattern; tables have header scopes; all actions are reachable by keyboard; toasts are announced.

### 5.6 i18n
New `Appointments` namespace in `ar.json` and `en.json` with identical keys: `title`, `subtitle`, `actions`, `filters`, `table`, `status`, `form`, `fields`, `validation`, `reschedule`, `cancel`, `statusDialog`, `states`, `pagination`, `toast`, `errors`, `devIdentity`. A one-off key-parity check runs as part of verification.

## 8. Acceptance criteria
- AC-1. List, filter (doctor/status/date range), and paginate appointments from the real API; loading, empty, error and no-identity states exist.
- AC-2. Booking works through doctor and patient selection with client validation mirroring the server; backend field errors, 404 and 409 are shown clearly and localized.
- AC-3. Reschedule changes only date/time; cancel requires a reason (≤ 500); status updates follow the role/status matrix (Complete only for Doctor).
- AC-4. Every user-facing string exists in `ar.json` and `en.json`; Arabic renders RTL and English LTR; logical utilities are used; times/phones do not reorder.
- AC-5. All API calls go through `lib/api`; identity headers are attached in one place and are inactive in production builds; no secret or token is stored or logged.
- AC-6. No medical data is requested, stored or displayed.
- AC-7. Accessibility basics hold: labelled inputs, error association, keyboard-operable dialogs with focus management, status not conveyed by color alone.
- AC-8. `npm run lint`, `npm run typecheck`, `npm run build` pass; automated tests pass (if approved); results reported honestly, including what could not be verified.
- AC-9. `HomeLanding.tsx`, the marketing header and the Payments feature are unchanged; no new runtime dependency.

## 9. Dependencies, risks, assumptions
- **Blocked by Q-C4-01/02** for the booking and filter screens to be usable.
- **R-1.** Backend work (lookups) enlarges the scope and must be agreed; the API contract becomes the frontend's dependency.
- **R-2.** Creating `components/ui` and `lib/api` sets shared conventions other members (Payments) will also use — coordinate to avoid duplicate primitives and merge conflicts.
- **R-3.** `cacheComponents` + `partialPrefetching` impose rules on dynamic data in Next 16; screens are client-driven (React Query), which avoids server-side dynamic access, but the build must confirm it.
- **R-4.** Without MySQL here, true end-to-end verification is limited to the stub-based browser check.
- **R-5.** Server messages are English-only until the optional `code` extension exists; generic localized messages may be less specific.
- **R-6.** The dev identity is a development tool; it must disappear with Q-07.
- **A-1.** Repository conventions (src layout, payments patterns) are followed over generic guidance.
- **A-2.** No new runtime dependency is needed (fetch + React Query + Zustand + toastify cover the needs).
