### Build-time notes / deviations to confirm
1. The approval text mentions a `Rescheduled` status. The agreed enum and DB CHECK have **no** such status (AGENTS.md §2: use only agreed statuses), so `Reschedule()` keeps the current status. Adding a status would need a schema change + migration — not done.
2. A `Create()` factory and a tiny `DomainException` were added (not in the approved method list) because "EndTime required in the Domain methods" cannot be enforced at creation otherwise (Class Spec §4.13 also lists `create()`).
3. The 500-character limit is a **domain rule**; the DB column is `text` (unchanged).
4. Domain methods take `clinicLocalNow` as a parameter; reading `Clinic:TimeZone` and computing it is the Application layer's job (F1-C2).
5. Legacy rows with `end_time = NULL` cannot be overlap-checked: `OverlapsInterval` throws `DomainException`; Application must handle/clean such rows.
6. Role rules for Completed/No-Show are **not** in Domain (Domain has no roles) — Application layer must enforce them. The exact role table is still to be confirmed.

## 1. Goal

Review and, where the approved rules require it, harden the `Appointment` persistence foundation so
later F1 cycles (application use cases, API, frontend) can rely on it:

1. Verify the `Appointment` entity and its relationships with `Doctor`, `Patient`, `Secretary`
   (via `doctor_secretaries`) and `MedicalVisit` against the Class Spec §4.13 / §4.12.
2. Verify database constraints, indexes, delete behavior and the EF Core configuration.
3. Decide (with approval) what the Domain layer must enforce for the time-interval rule.
4. Establish test coverage for the domain/model rules of F1-C1.

Out of scope for F1-C1: services/handlers, DTOs, validators, AutoMapper maps, controllers, auth,
frontend, pagination contract (Q-04). Those belong to later F1 cycles.

### 3.2 Gaps, risks and ambiguities found

| # | Finding | Impact | Needs |
|---|---|---|---|
| G-1 | **`EndTime` is nullable.** AGENTS.md's overlap formula needs an `existingEnd`/`newEnd`; with `NULL` the interval is undefined. The Class Spec leaves `endTime` optional. | Overlap rule cannot be applied to appointments with no end time | **Q-F1-01** |
| G-2 | **No database-level overlap protection.** MySQL has no exclusion constraints; the index is non-unique. Overlap can only be enforced in the Application flow. - B-2. **Controlled state changes on `Appointment`** (needs Q-F1-02, Q-F1-03, Q-09): `Reschedule(date, start, end)`, `Cancel(reason)`, `UpdateStatus(status)` that enforce the approved lifecycle. - B-3. **Schema change, only if approved**: e.g. make `end_time` NOT NULL (Q-F1-01), or add a DB-level defense against exact-duplicate slots (Q-F1-04). Any change = **one new migration** generated from the agreed integration state; `InitialCreate` is never edited (AGENTS.md §4.3).

## 10. Risks and assumptions

- **R-1.** Overlap checked only in Application + race condition → double booking. Mitigation to be designed in F1-C2 (transaction + locking, or DB-level defense per Q-F1-04).
- **R-2.** MySQL has no partial/filtered unique index, so "unique active slot" cannot be done declaratively without a generated column.
- **R-3.** Tightening setters on `Appointment` may ripple into later cycles → default is to add behavior without removing setters.
- **R-4.** Oracle `MySql.EntityFrameworkCore` license approval (GPL-2.0 with FOSS exception) is still pending team decision (noted in PERSISTENCE_FOUNDATION); outside C1 but affects the whole DB layer.
- **Assumption:** the repository (not AGENTS.md's path names) is the technical source of truth; the DB engine is MySQL as already implemented (Q-10 is formally still open).
