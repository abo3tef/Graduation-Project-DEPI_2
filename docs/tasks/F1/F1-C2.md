## 1. Goal

Implement the Application-layer use cases for appointments, enforcing every business rule on the
server, independent of any UI:

1. **Book** an appointment.
2. **Reschedule** (date/time only).
3. **Cancel** (mandatory reason).
4. **Update status** (Confirm / Complete / No-Show) with role rules.
5. **View** one appointment and **list** appointments (filtered, paginated, ordered).

Rules enforced: secretary ↔ assigned-doctor scope (BRULE-10), no overlap per doctor (Cancelled and
No-Show free the slot), past-date rejection using `Clinic:TimeZone`, legacy `end_time = NULL` handling,
concurrency protection, FluentValidation validators, explicit AutoMapper mapping.

**Out of scope:** HTTP controllers/routes/OpenAPI (F1-C3), frontend (F1-C4+), authentication itself
(Q-07), payments (F2), medical data access of any kind, schema changes/migrations.

## 3. Current code state (inspected)

- `Medilog.Application` references **only** `Medilog.Domain`. It contains `AddApplication()` (FluentValidation + AutoMapper scanning), an empty `MappingProfile`, and empty folders (`Features/Appointments`, `Interfaces`, `DTOs`, `Common`, …) holding only `.gitkeep`. **No service, handler, port, DTO, or validator exists to copy a pattern from.**
- `Medilog.Infrastructure` has `MedilogDbContext` (MySQL) and an `AddInfrastructure()` that only registers the context. No Application port is implemented.
- `Medilog.WebAPI`: `AddControllers()`, `AddProblemDetails()`, `UseExceptionHandler()`, `UseAuthorization()`; **no authentication, no controllers, no exception→HTTP mapping, no current-user abstraction**. (Q-07 open.)
- No pagination DTO/contract exists (Q-04 open). No test project (Q-F1-08).
- `Appointment` (C1) provides `Create`, `Reschedule`, `Cancel`, `UpdateStatus`, `OverlapsWith`, `OverlapsInterval`, `IsOpen`, `OccupiesSlot`; throws `DomainException`.
- Secretary ⇄ Doctor is the EF many-to-many `Secretary.Doctors` / `Doctor.Secretaries` over `doctor_secretaries`.
- `Patient.DoctorId` is nullable (documented); `Appointment.CreatedBy` has no FK and must be validated by the Application.

Because the Application layer is empty, **C2 sets the first backend patterns for the whole project** (data access, current user, error handling). That is why several questions below are blocking.

### 4.2 Use cases (all take `CancellationToken`; all derive actor from `ICurrentUser`)

**Common guards (every use case)**
1. Actor must be an active Doctor or Secretary (Inactive account → rejected).
2. Doctor actor: only appointments where `DoctorId == actor.Id`.
3. Secretary actor: only appointments whose `DoctorId` is in the secretary's assigned doctors (`doctor_secretaries`). Out-of-scope IDs return **Not Found** (not Forbidden) so existence is not leaked.
4. Any other role → Forbidden. Medical data is never loaded or returned.

**Book** (`BookAppointmentRequest`: patientId, doctorId, appointmentDate, startTime, endTime, reason)
1. Validate request shape (validator).
2. Resolve doctor; secretary ⇒ doctor must be assigned (BRULE-10); doctor must be Active.
3. Resolve patient; must satisfy the doctor–patient rule (**Q-C2-07**; proposed: `Patient.DoctorId == doctorId`).
4. Normalize times to whole seconds (column is `time(0)`); reject local times that do not exist in the clinic timezone (DST gap).
5. `clinicLocalNow` from `IClinicClock`.
6. Begin transaction + per-doctor lock (§4.4).
7. Conflict check (§4.3) → Conflict (409) if any.
8. `Appointment.Create(patientId, doctorId, createdBy = actor.Id, …)` → save → commit → map to response.

**Reschedule** (`RescheduleAppointmentRequest`: appointmentDate, startTime, endTime)
Load for scope → lock doctor → **re-read the appointment inside the lock** → conflict check excluding itself → `appointment.Reschedule(...)` (Domain enforces open status, interval, past) → save. Patient/doctor never change; reason/notes unchanged.

**Cancel** (`CancelAppointmentRequest`: cancellationReason)
Scope → lock → re-read → `appointment.Cancel(reason)` → save. Slot is freed automatically (status).

**Update status** (`UpdateAppointmentStatusRequest`: status ∈ Confirmed / Completed / NoShow; `Cancelled` rejected — use cancel)
Scope → role permission (§4.5) → lock → re-read → `appointment.UpdateStatus(status)` → save.

**Get by id / List**
- Get: scope-filtered; response contains appointment fields + patient `FullName`/`Phone` and doctor `FullName` only (minimum administrative info; no medical fields).
- List filters (all optional): doctorId, patientId, dateFrom, dateTo, status. A secretary's query is **always** intersected with assigned doctors; a doctor's with their own id (client-supplied doctor filters can only narrow, never widen).
- Ordering: `AppointmentDate, StartTime, Id` (deterministic with stable tie-breaker). Pagination per the shared contract (**Q-C2-04**). Filtering and counting in the database; projection straight to the response.

### 4.3 Overlap prevention
- Candidate set (database): `DoctorId == X`, `AppointmentDate == D`, `Status` not `Cancelled`/`No-Show`, `Id != self` (reschedule). This is bounded (one doctor, one day), uses index `ix_appointments_doctor_id_appointment_date_start_time`.
- Rule evaluated with the **Domain** method `OverlapsInterval` (single source of truth, formula `newStart < existingEnd && newEnd > existingStart`; exact adjacency allowed; partial, containment, identical rejected).
- **Legacy rows with `end_time = NULL`** (**Q-C2-08**): `OverlapsInterval` throws for them by design. Proposed policy: the service treats such a row as a zero-length point at `StartTime` (conflict iff `candStart <= existing.Start < candEnd`), logs a non-sensitive warning with the appointment id, and never crashes the request. No data migration (approved: no schema change).
- Other doctors' dates/doctors never conflict; patient double-booking across different doctors is **not** a rule in the spec and is not enforced (assumption **A-3**).

### 4.4 Concurrency protection (no schema change, MySQL/InnoDB)
- Every mutating use case runs in one DB transaction whose **first statement** is a locking read of the doctor row (`SELECT id FROM doctors WHERE id = @id FOR UPDATE`), implemented in Infrastructure behind the Application port. This serializes bookings/reschedules/cancels/status changes **per doctor**; different doctors do not block each other.
- The conflict query and the write happen inside that lock; commit releases it. A lock-wait timeout/deadlock is surfaced as a retryable Conflict/ServiceUnavailable, never swallowed.
- Appointment state is re-read inside the lock, so stale-state races (cancel vs confirm) are decided deterministically.
- No `rowversion`/unique-slot constraint is added (no migration approved). This protects all writes that go through the service; direct SQL bypasses it (accepted, documented).
- Verification needs a real MySQL (**Q-C2-09**).

### 4.5 Role rules for status changes (proposal — needs confirmation, Q-C2-06)
| Action | Doctor (own appointments) | Secretary (assigned doctors) |
|---|---|---|
| Book / Reschedule / Cancel | Yes | Yes |
| Confirm (Scheduled → Confirmed) | Yes | Yes |
| Mark No-Show | Yes | Yes (front desk knows who did not arrive) |
| Mark Completed | Yes | **No** (outcome of the consultation belongs to the doctor) |

### 4.6 Clinic time and past-date rule
- `IClinicClock.LocalNow` converts `UtcNow` with `TimeZoneInfo.FindSystemTimeZoneById(config["Clinic:TimeZone"])`.
- Missing/invalid timezone → **fail clearly at startup/first use**; never fall back to UTC (PERSISTENCE_FOUNDATION §8.2).
- Past rejection is enforced by the Domain (`clinicLocalNow` passed in); the validator does **not** duplicate it.
- Local start/end times that do not exist in the timezone (DST gap) are rejected; ambiguous times (fall-back) are accepted as wall-clock values because appointments are stored as clinic wall-clock time (documented, no conversion).
- Egypt observes DST (since 2023), so these two cases are real, not theoretical.

### 4.7 FluentValidation (shape only; invariants stay in Domain)
| Request | Rules |
|---|---|
| Book | patientId/doctorId not empty; date not default; start/end present; `end > start`; `reason` ≤ max length (proposed 1000, **Q-C2-10**) |
| Reschedule | date not default; start/end present; `end > start` |
| Cancel | reason not blank after trim; ≤ 500 |
| UpdateStatus | status is a defined enum value; `Cancelled` rejected |
| List | page ≥ 1; page size within the team-approved maximum; `dateFrom ≤ dateTo`; status defined |

Validators are registered by the existing assembly scan in `AddApplication()`; the service invokes them, and failures return the shared error shape.

### 4.8 AutoMapper
Explicit `Appointment → AppointmentResponse` map (patient/doctor names, status label, ids). **No** request → entity maps. `CreatedBy` is set only from `ICurrentUser`. Note: AutoMapper 16 is commercial; the key is supplied by `AUTOMAPPER_LICENSE_KEY` (existing note in `DependencyInjection.cs`) — verify it works in the Tech Lead's environment.

## 7. Acceptance criteria

- AC-1. Book, reschedule, cancel, update status, get, list are implemented in Application behind `IAppointmentService`, thin and free of EF/HTTP types.
- AC-2. A secretary can act only on assigned doctors; every out-of-scope access is rejected without revealing existence; the actor is taken only from `ICurrentUser`.
- AC-3. Overlap rule per AGENTS formula; Cancelled/No-Show free the slot; reschedule excludes itself; legacy null-end rows handled per the approved policy.
- AC-4. Past appointments rejected using `Clinic:TimeZone` (`Africa/Cairo`); invalid config fails clearly; DST gap handled.
- AC-5. Concurrent bookings for the same doctor cannot double-book (verified against real MySQL, or reported as not verified).
- AC-6. Validators exist for every request/query and are registered centrally.
- AC-7. No request is mapped onto an entity; no EF entity is returned; no medical data exposed.
- AC-8. `dotnet build backend/Medilog.sln` 0 warnings/0 errors; `dotnet ef migrations has-pending-model-changes` clean; tests run per Q-C2-05 with real results reported.
- AC-9. No migration, no unrelated changes (`HomeLanding.tsx` untouched).

## 8. Dependencies, risks, assumptions

- **Blocked/affected by open decisions:** Q-04 (pagination contract), Q-05 (patterns), Q-07 (authentication/roles), Q-02 (doctor–patient relationship).
- **R-1.** Setting the first Application patterns here may conflict with what other members build in parallel — align with Member 6/Tech Lead before `build`.
- **R-2.** Without authentication, C2 can be verified only through tests/harness, not over HTTP.
- **R-3.** Per-doctor lock depends on InnoDB row locking; a different DB engine (Q-10) would need a different lock.
- **R-4.** Clinic timezone data must exist on the host (`Africa/Cairo` requires tz/ICU data on the server).
- **A-1.** Repository files, not `AGENTS.md` path names, are the source of truth (carried from C1).
- **A-2.** No working-hours, maximum duration, or maximum-days-ahead rule exists in the spec; none will be invented.
- **A-3.** Spec forbids only same-**doctor** overlap; a patient with two simultaneous appointments with different doctors is allowed.
