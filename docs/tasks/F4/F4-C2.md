## 1. Goal

Give an authenticated doctor a write API over the persisted medical core: create a visit, read one
visit with its diagnoses, update the allowed visit fields, and add/update diagnoses on that visit —
all scoped to the acting doctor, validated in the Application layer, and mapped through AutoMapper
without exposing EF entities.

This is the **first HTTP surface in the repository**; it therefore also establishes the API
convention (controller shape, error shape, route naming) that F1/F3/F5 will follow.

## 5. API contract

Base route: `/api/medical-visits`. All endpoints require an authenticated **Doctor** (C2b).

| # | Method | Route | Body | Success | Error codes |
|---|---|---|---|---|---|
| 1 | `POST` | `/api/medical-visits` | `CreateMedicalVisitRequest` | `201` + `Location` + `MedicalVisitResponse` | 400, 401, 403, 404, 409 |
| 2 | `GET` | `/api/medical-visits/{visitId:guid}` | — | `200` `MedicalVisitResponse` | 401, 403, 404 |
| 3 | `PUT` | `/api/medical-visits/{visitId:guid}` | `UpdateMedicalVisitRequest` | `200` `MedicalVisitResponse` | 400, 401, 403, 404 |
| 4 | `POST` | `/api/medical-visits/{visitId:guid}/diagnoses` | `CreateDiagnosisRequest` | `201` + `Location` + `DiagnosisResponse` | 400, 401, 403, 404 |
| 5 | `PUT` | `/api/medical-visits/{visitId:guid}/diagnoses/{diagnosisId:guid}` | `UpdateDiagnosisRequest` | `200` `DiagnosisResponse` | 400, 401, 403, 404 |

**Deliberately absent:** `DELETE …/diagnoses/{id}` (D-12) and any list endpoint (Q-04).

### 5.1 Requests

```text
CreateMedicalVisitRequest
  Guid            PatientId        required, non-empty
  Guid?           AppointmentId    optional; if present must belong to the same patient AND doctor
  DateTimeOffset  VisitDate        required; stored as UTC
  string?         ChiefComplaint   ≤ 2000
  string?         Symptoms         ≤ 2000
  string?         ClinicalNotes    ≤ 4000   (only if Q-08 keeps clinical notes)

UpdateMedicalVisitRequest      // mutable fields only
  DateTimeOffset  VisitDate
  string?         ChiefComplaint
  string?         Symptoms
  string?         ClinicalNotes
  // PatientId / DoctorId / AppointmentId are immutable after creation

CreateDiagnosisRequest
  string   DiagnosisName   required, ≤ 200
  string?  Description     ≤ 4000
  DateOnly DiagnosisDate   required

UpdateDiagnosisRequest
  string   DiagnosisName
  string?  Description
  DateOnly DiagnosisDate
```

### 5.2 Responses

```text
MedicalVisitResponse
  Guid Id, PatientId, DoctorId; Guid? AppointmentId
  DateTimeOffset VisitDate
  string? ChiefComplaint, Symptoms, ClinicalNotes
  IReadOnlyList<DiagnosisResponse> Diagnoses

DiagnosisResponse
  Guid Id, VisitId, PatientId
  string DiagnosisName; string? Description; DateOnly DiagnosisDate
```

`PatientId` is included because the client needs it for navigation; **no patient name, no
`PasswordHash`, no doctor email, no EF entity is ever returned** (`AGENTS.md` §4.4, §5).

### 5.3 Error shape

RFC 7807 `ProblemDetails`. Validation failures use `ValidationProblemDetails` with a
`errors: { field: [messages] }` map (MVC's `[ApiController]` produces this once model state is
invalid). Application exceptions map to:

| Exception | Status | `title` |
|---|---|---|
| `ValidationException` (FluentValidation) | 400 | `One or more validation errors occurred.` |
| `NotFoundException` | 404 | `Resource not found.` |
| `ForbiddenException` | 403 | `Forbidden.` |
| `ConflictException` | 409 | `The request conflicts with the current state.` |

**No internal exception message, stack trace, SQL text, or patient data in any response.**

### 5.4 Route/contract decisions to record

- Route uses `medical-visits` (kebab-case) and `diagnoses` as sub-resource — this sets the naming
  convention for F1/F3/F5 and must be accepted by FS before merge.
- No API versioning (nothing in the repo uses it); flagged for FS.

## 6. Application use cases (plain services — D-08)

One interface, `IMedicalVisitService`, with five methods. `MedicalVisitService` implements all of
them and is registered with `AddScoped`. No MediatR, no pipeline behaviour.

| # | Use case | Signature | Responsibility |
|---|---|---|---|
| 6.1 | `CreateVisitAsync` | `Task<MedicalVisitResponse> CreateVisitAsync(CreateMedicalVisitRequest, CancellationToken)` | Validate; resolve acting doctor (§8); verify patient exists and is in the doctor's workspace; verify appointment belongs to the same patient+doctor and is not already linked; construct `MedicalVisit` with `DoctorId` from `ICurrentUser`; save; return mapped response |
| 6.2 | `GetVisitAsync` | `Task<MedicalVisitResponse> GetVisitAsync(Guid visitId, CancellationToken)` | Load visit **scoped to the acting doctor**, `AsNoTracking`, `Include(Diagnoses)`; 404 if not found or out of scope |
| 6.3 | `UpdateVisitAsync` | `Task<MedicalVisitResponse> UpdateVisitAsync(Guid visitId, UpdateMedicalVisitRequest, CancellationToken)` | Validate; load scoped tracked visit; apply **only** mutable fields; save; return mapped response |
| 6.4 | `AddDiagnosisAsync` | `Task<DiagnosisResponse> AddDiagnosisAsync(Guid visitId, CreateDiagnosisRequest, CancellationToken)` | Validate; load scoped visit; copy `PatientId` **from the visit** (never from the request); save |
| 6.5 | `UpdateDiagnosisAsync` | `Task<DiagnosisResponse> UpdateDiagnosisAsync(Guid visitId, Guid diagnosisId, UpdateDiagnosisRequest, CancellationToken)` | Validate; load diagnosis through its visit, scoped to the acting doctor; apply mutable fields; save |

Validation entry point (replaces the MediatR pipeline):

- Each public method calls `await validator.ValidateAndThrowAsync(request, cancellationToken)` as its
  **first** statement, using the concrete `IValidator<TRequest>` injected into the service.
- Therefore validation cannot be bypassed by calling the service from a controller, a job, or a test.

Service rules:

- Every method is `async`, takes `CancellationToken`, and carries the `Async` suffix
  (`AGENTS.md` §4.2).
- No HTTP types in Application; no `IActionResult`.
- Validators check **input shape**; the service checks **state** (existence, ownership, appointment
  consistency). No rule is duplicated across both.
- `Guid.Empty` is rejected for every identifier (§7).

## 7. Validation rules

### 7.1 `CreateMedicalVisitRequestValidator`

| Rule | Severity |
|---|---|
| `PatientId` not `Guid.Empty` | error |
| `AppointmentId`, when present, not `Guid.Empty` | error |
| `VisitDate` required and not `default(DateTimeOffset)` | error |
| `VisitDate` not more than 5 minutes in the future | error — **assumption**, confirm with Cycle owner |
| `ChiefComplaint` ≤ 2000, `Symptoms` ≤ 2000, `ClinicalNotes` ≤ 4000 | error |
| No whitespace-only strings (normalized to `null` if empty after trim) | error |

### 7.2 `UpdateMedicalVisitRequestValidator`

Same string/date rules as 7.1 minus the identifiers. `PatientId`/`DoctorId` are not accepted at all,
so they can never be overwritten (`AGENTS.md` §3.3).

### 7.3 `CreateDiagnosisRequestValidator` / `UpdateDiagnosisRequestValidator`

| Rule | Severity |
|---|---|
| `DiagnosisName` required, trimmed, ≤ 200 | error |
| `Description` ≤ 4000 | error |
| `DiagnosisDate` required, not `default(DateOnly)` | error |
| `DiagnosisDate` not in the future | error — **assumption**, confirm |
| `DiagnosisDate` lies inside the visit's lifetime window | **not enforced in C2** — a visit has no end date; recorded as a limitation |

### 7.4 Business invariants enforced in the handler (not the validator)

1. Patient exists → else 404.
2. Patient is in the acting doctor's workspace (§8) → else 403.
3. `AppointmentId`, when supplied, belongs to the same `PatientId` and `DoctorId` → else 400.
4. The appointment is not already linked to another visit (unique index) → else 409.
5. Diagnosis's `PatientId` is taken from the loaded visit, never from the request.

> **No `MedicalVisit.AddDiagnosis(...)` domain method is added in this Cycle.** The entities are
> plain data holders today; introducing domain behaviour is a separate, reviewable change and
> would also require deciding aggregate boundaries. Recorded so it is not forgotten.

## 8. Authorization and data scoping

| Rule | Implementation point |
|---|---|
| Only the `Doctor` role may call any endpoint | MVC policy `[Authorize(Roles = "Doctor")]` or a named policy (C2b) |
| Acting doctor id comes from the authenticated principal | `ICurrentUser` (D-11) |
| A doctor may read/update a visit only when `visit.DoctorId == actingDoctorId` | Query filter inside each handler |
| A doctor may create a visit only for a patient in their workspace | `patient.DoctorId == actingDoctorId` |
| **Assumed** workspace rule (Q-02): a patient has exactly one owning doctor | §0.3 — requires Tech Lead confirmation |
| Secretary has no access to any route in this Cycle | No secretary policy is granted; covered by a test |
| Not-found vs forbidden | Out-of-scope records return **404** (do not reveal that the record exists) |

## 9. Persistence rules the handlers must honour

1. `SaveChangesAsync(ct)` only — never `SaveChanges()`.
2. No raw SQL, no `ExecuteUpdate`; EF entities only.
3. `AsNoTracking()` on every read query.
4. Include only what the response needs (`Include(v => v.Diagnoses)`); no cartesian explosion.
5. Deterministic ordering before any projection: `Diagnoses.OrderBy(d => d.DiagnosisDate).ThenBy(d => d.Id)`.
6. Never assign `VisitId`/`PatientId` from the client for a diagnosis.
7. No migration: if `dotnet ef migrations has-pending-model-changes` reports anything, the Cycle is
   wrong and must be reverted.

## 10. AutoMapper rules

| Map | Direction | Notes |
|---|---|---|
| `CreateMedicalVisitRequest → MedicalVisit` | input → **new** entity only | Explicitly ignore `Id`, `DoctorId`, `Patient`/`Doctor`/`Appointment` navs, and all child collections; the service sets `DoctorId` itself |
| `UpdateMedicalVisitRequest → MedicalVisit` | input → **existing tracked** entity, **only** `VisitDate`, `ChiefComplaint`, `Symptoms`, `ClinicalNotes` | `ForMember(...)` for the four members and `Ignore()` every other member — the profile must make the ignored set explicit |
| `Diagnosis → DiagnosisResponse`, `MedicalVisit → MedicalVisitResponse` | entity → DTO | Explicit child mapping |
| `CreateDiagnosisRequest → Diagnosis` | input → new entity | Ignore `Id`, `VisitId`, `PatientId`, navs |

Forbidden: convention-based bulk mapping of a request onto a tracked entity; any map that copies
`Id`, `DoctorId`, `PatientId` (for diagnoses), or navigation properties from client input.

## 18. C2b implementation plan (approved 2026-11-11)

The HTTP slice is deliberately thin. The controller contains no validation, no persistence query
and no ownership rule: it calls one `IMedicalVisitService` method and maps the result to HTTP.

| # | Endpoint | Action | Success | `Location` |
|---|---|---|---|---|
| 1 | `POST /api/medical-visits` | `CreateVisitAsync` | 201 | `GET /api/medical-visits/{id}` |
| 2 | `GET /api/medical-visits/{visitId:guid}` | `GetVisitAsync` | 200 | — |
| 3 | `PUT /api/medical-visits/{visitId:guid}` | `UpdateVisitAsync` | 200 | — |
| 4 | `POST /api/medical-visits/{visitId:guid}/diagnoses` | `AddDiagnosisAsync` | 201 | parent visit (`GET /api/medical-visits/{visitId}`) |
| 5 | `PUT /api/medical-visits/{visitId:guid}/diagnoses/{diagnosisId:guid}` | `UpdateDiagnosisAsync` | 200 | — |

### 18.1 WebAPI pipeline

1. `AddAuthentication(JwtBearerDefaults.AuthenticationScheme).AddJwtBearer()` — validation only,
   no token issuance (D-16).
2. `AddAuthorization()` + `[Authorize(Roles = Roles.Doctor)]` on the controller (D-18).
3. `AddHttpContextAccessor()` + `ICurrentUser` → `CurrentUser` (claims `sub`/`role`).
4. `AddExceptionHandler<GlobalExceptionHandler>()` + the existing `AddProblemDetails()` and
   `UseExceptionHandler()`.
5. `UseAuthentication()` before `UseAuthorization()`.

### 18.2 Error mapping

| Exception | Status | Body |
|---|---|---|
| FluentValidation `ValidationException` | 400 | `ValidationProblemDetails` with `errors` grouped by property |
| `NotFoundException` | 404 | `ProblemDetails`, title `Resource not found.` |
| `ForbiddenException` | 403 | `ProblemDetails`, title `Forbidden.` |
| `ConflictException` | 409 | `ProblemDetails`, title `The request conflicts with the current state.` |
| any other | 500 | generic `ProblemDetails`; the exception is logged, never returned |

No `exception.Message`, stack trace, SQL text or patient data is written to a response.

### 18.3 Test project (D-19)

`backend/tests/Medilog.WebAPI.Tests` runs the real `Program` pipeline with:
- `WebApplicationFactory<Program>` and a throwaway EF InMemory database (the MySQL registration is
  replaced in `ConfigureTestServices`);
- a `TestAuthHandler` that reads `X-Test-UserId` / `X-Test-Role`, so no real token is needed;
- `IApplicationDbContext` **not** overridden, which makes the tests exercise the D-21 registration.

Cases: success 201/200 for all five routes, `Location` header, anonymous 401, secretary 403,
foreign visit 404, foreign patient 403, appointment mismatch 400, duplicate appointment 409,
`ProblemDetails` shape with no stack trace, and the absent list/delete routes (405).

### 18.4 Development token

```bash
# Use the doctor id as the token name: 'dotnet user-jwts' always writes the name into 'sub',
# and passing --claim "sub=..." would create a multi-valued claim.
dotnet user-jwts create \
  --project backend/src/Medilog.WebAPI \
  --name "<doctor-guid>" \
  --role Doctor
```

The signing key is stored in user secrets; `appsettings*.json` contains no secret. A production
deployment must supply the real issuer, audience and signing keys through configuration.

### 18.5 Out-of-scope guardrails specific to C2b

- No `login`, `register`, `refresh` or password route.
- No `Authorize` policy for Secretary; the medical controller is doctor-only.
- No `GET` list, no diagnosis `GET`, no `DELETE`.
- No EF query or `SaveChanges` in the controller.
- No migration and no Domain change.
