## 1. Goal

Give an authenticated doctor a usable Next.js surface for the medical-record endpoints that already
exist:

1. record a new medical visit for a patient in their workspace;
2. open a visit and read its current clinical content;
3. edit the visit's own fields;
4. add and edit diagnoses;
5. add, edit and delete prescribed medication lines;
6. see the result of every action without a page reload, with clear loading, empty, validation and
   failure states in Arabic (RTL) and English (LTR).

The frontend must not weaken the backend contract: it never sends a doctor id, never invents a
medical field, never hides a server error behind a generic message, and never stores the token
anywhere but `sessionStorage` in development.

## 2. Scope

### In scope

1. A typed API layer (`src/lib/api/`) for exactly the eight endpoints in §5.
2. A development-only token bridge (D-28).
3. Three routes (D-30) and the feature module `features/medical-records`.
4. Visit create/edit forms, diagnosis add/edit forms, medication add/edit forms and delete
   confirmation.
5. Server-state hooks (TanStack Query) with deterministic cache keys and targeted invalidation.
6. Loading, empty, success, validation, `401`, `403`, `404`, `409` and network-failure states.
7. Arabic and English translations for every new string.
8. `frontend/.env.example` documenting `NEXT_PUBLIC_API_BASE_URL` (no secret values).
9. One localised `Header` link to `/medical-records` (D-31).

### Out of scope (explicitly)

- Login, registration, token refresh, password reset, OTP, role provisioning.
- Any backend change: no new endpoint, DTO, validator, migration or CORS change.
- A visit/patient **list**, search, filtering or pagination (Q-04).
- A real patient picker fed by patient data — the create page takes a `patientId` from the URL.
- Secretary screens; anything that would expose medical data to a non-doctor role.
- Diagnosis delete, visit delete, medication restore/undo (not in the contract).
- Prescription printing, PDF export, e-signature, templates.
- Dashboard, timeline, appointments UI.
- New npm dependencies (including test frameworks, form libraries, schema validators, Axios).
- Choosing the shared pagination/error envelope (Q-04) or the real auth flow (Q-07 remains
  answered only for the backend).

## 5. API surface consumed (unchanged)

Base URL: `NEXT_PUBLIC_API_BASE_URL` → `http://localhost:5208` by default.

| # | Method | Route | Request | Success | UI trigger |
|---|---|---|---|---|---|
| 1 | `GET` | `/api/medical-visits/{visitId}` | — | `200` `MedicalVisitResponse` | Detail page load / refetch |
| 2 | `POST` | `/api/medical-visits` | `CreateMedicalVisitRequest` | `201` `MedicalVisitResponse` | Create form submit |
| 3 | `PUT` | `/api/medical-visits/{visitId}` | `UpdateMedicalVisitRequest` | `200` `MedicalVisitResponse` | Edit form submit |
| 4 | `POST` | `/api/medical-visits/{visitId}/diagnoses` | `CreateDiagnosisRequest` | `201` `DiagnosisResponse` | “Add diagnosis” |
| 5 | `PUT` | `/api/medical-visits/{visitId}/diagnoses/{diagnosisId}` | `UpdateDiagnosisRequest` | `200` `DiagnosisResponse` | “Edit diagnosis” |
| 6 | `POST` | `/api/medical-visits/{visitId}/medications` | `CreateMedicationRequest` | `201` `MedicationResponse` | “Add medication” |
| 7 | `PUT` | `/api/medical-visits/{visitId}/medications/{medicationId}` | `UpdateMedicationRequest` | `200` `MedicationResponse` | “Edit medication” |
| 8 | `DELETE` | `/api/medical-visits/{visitId}/medications/{medicationId}` | — | `204` | Confirmed delete (D-23) |

Rules the client must respect:

- Send `Authorization: Bearer <token>` and `Accept: application/json` on every call; `Content-Type:
  application/json` only when a body exists.
- Never send `doctorId`, `patientId` inside visit update, or any route/body id other than the ones
  listed above.
- After every successful child mutation, invalidate **only** `['medical-records','visit',visitId]`.
- Treat `Location` as informational; use the response body `id` for navigation.
- Use `cache: 'no-store'` on the visit `GET` (token-scoped data must not land in a shared cache).

### 5.1 Client-side payload shapes

```text
CreateMedicalVisitRequest      patientId, appointmentId?, visitDate, chiefComplaint?,
                               symptoms?, clinicalNotes?
UpdateMedicalVisitRequest      visitDate, chiefComplaint?, symptoms?, clinicalNotes?
CreateDiagnosisRequest         diagnosisName, description?, diagnosisDate        // YYYY-MM-DD
UpdateDiagnosisRequest         diagnosisName, description?, diagnosisDate
CreateMedicationRequest        medicationName, dosage, frequency, duration?, instructions?
UpdateMedicationRequest        medicationName, dosage, frequency, duration?, instructions?

MedicalVisitResponse           id, patientId, doctorId, appointmentId?, visitDate,
                               chiefComplaint?, symptoms?, clinicalNotes?,
                               diagnoses: DiagnosisResponse[], medications: MedicationResponse[]
DiagnosisResponse              id, visitId, patientId, diagnosisName, description?, diagnosisDate
MedicationResponse             id, visitId, patientId, medicationName, dosage, frequency,
                               duration?, instructions?
ValidationProblemDetails       type?, title?, status, detail?, instance?, errors?: Record<string,string[]>
```

`null`-able fields are typed `string | null` (not optional) because the API returns explicit
`null`s. No `any` anywhere; unknown JSON is narrowed at the boundary in `src/lib/api`.

## 6. Routes and page composition

Every page stays a thin composition layer; the work lives in the feature module.

| Route | File | Behaviour |
|---|---|---|
| `/{locale}/medical-records` | `app/[locale]/medical-records/page.tsx` | Workspace: token status (D-28), “open visit by id”, link to create |
| `/{locale}/medical-records/visits/new` | `app/[locale]/medical-records/visits/new/page.tsx` | Create form; reads `?patientId=` as the initial value (editable, GUID-validated) |
| `/{locale}/medical-records/visits/[visitId]` | `app/[locale]/medical-records/visits/[visitId]/page.tsx` | Detail: visit summary + inline edit, diagnoses section, medications section |

- A small `medical-records/layout.tsx` provides the page chrome (`min-h-dvh`, surface card
  container, back link). It reuses the existing colour/typography tokens; no redesign of the
  marketing pages.
- Because the token lives in the browser (D-28), all data-touching components are **client
  components**. Pages only resolve `params`/`searchParams` and render the feature component; no
  server-side `fetch` to the API is introduced, which also avoids caching a doctor-scoped payload.
- Implementation constraint from `cacheComponents: true`: a page that reads `searchParams`
  (`visits/new?patientId=`) must sit behind a `<Suspense>` boundary, and route params must be read
  with `useParams()` in the client component (or awaited in the server page). The plan assumes this
  is handled inside the route files, not with `export const dynamic = 'force-dynamic'` sprinkled
  around.
- `notFound()` is **not** used for a `404` from the API (that would be indistinguishable from a bad
  route); a localised “visit not found / not in your workspace” state is rendered instead.
- Invalid `visitId` (not a GUID) renders the same not-found state without calling the API.

## 8. Data layer

### 8.1 `src/lib/api/`

- `env.ts` — resolves `NEXT_PUBLIC_API_BASE_URL`, trims a trailing slash, falls back to
  `http://localhost:5208`, and exposes it as a `string`.
- `problem-details.ts` — `ProblemDetails` / `ValidationProblemDetails` types, a runtime guard, and
  `readFieldErrors(problem): Record<string, string[]>` normalising keys case-insensitively so
  `MedicationName` and `medicationName` both map to one form field.
- `api-client.ts` — `request<T>(path, {method, body, signal})`:
  - builds the URL, attaches `Authorization` when a token exists;
  - parses JSON only when a body is present, tolerating an empty `204`;
  - throws `ApiError` with `status`, `problem`, `fieldErrors`, and a `kind`
    (`'unauthorized' | 'forbidden' | 'not-found' | 'conflict' | 'validation' | 'network' | 'server'`);
  - never logs the token or the response body.
- `index.ts` — barrel.

### 8.2 Token store (D-28)

`use-dev-token.ts` exposes `readToken`, `saveToken`, `clearToken`, `hasToken`. Storage key
`medilog.dev-token` in `sessionStorage` only. Reads are guarded for SSR (`typeof window`), and the
component rendering the panel is only mounted when `process.env.NODE_ENV === 'development'`.

### 8.3 Feature API + hooks

- `api.ts` — the eight functions from §5, each typed with the shapes in §5.1.
- `keys.ts` — `medicalVisitKeys.detail(visitId)` → `['medical-records','visit',visitId]`.
- `hooks/use-medical-visit.ts` — `useQuery` wrapper with `enabled: Boolean(visitId && token)`.
- `hooks/use-visit-mutations.ts`, `hooks/use-diagnosis-mutations.ts`,
  `hooks/use-medication-mutations.ts` — `useMutation` wrappers that:
  - call the API;
  - show `notify.success` / `notify.error` with **translated** messages;
  - invalidate `medicalVisitKeys.detail(visitId)` on success (and only then);
  - expose `fieldErrors` to the form so `400` responses land on the right inputs.
- Never mirror server state in Zustand; `useUiStore` remains untouched.

## 9. Validation (client-side, UX only)

Mirrors the documented server limits; the server remains authoritative and is re-checked on every
submit.

| Field | Client rule |
|---|---|
| `patientId` | Required, GUID |
| `appointmentId` | Optional, GUID when present |
| `visitDate` | Required, not in the future (compared against `now`) |
| `chiefComplaint`, `symptoms` | Optional, ≤ 2000 |
| `clinicalNotes` | Optional, ≤ 4000 |
| `diagnosisName` | Required, ≤ 200, non-whitespace |
| `diagnosisDate` | Required, not in the future |
| `description` | Optional, ≤ 4000 |
| `medicationName` | Required, ≤ 200 |
| `dosage`, `frequency` | Required, ≤ 100 |
| `duration` | Optional, ≤ 100 |
| `instructions` | Optional, ≤ 4000 |

Behaviour: validate on submit (and re-validate on change after the first submit attempt); send
trimmed required values and omit/`null` empty optionals; map server field errors over client ones;
keep the entered values after a failed submit; disable the submit button while pending and prevent
double submission.

Date handling (a real bug source): `<input type="datetime-local">` returns wall-clock text with no
offset — convert with `new Date(value)` → `.toISOString()` before sending. `diagnosisDate` stays a
plain `YYYY-MM-DD` string in both directions, and is displayed by parsing it as a **UTC** date so
the day never shifts by timezone.

## 10. States to implement

| State | Where | Behaviour |
|---|---|---|
| Token missing | Workspace + detail + new | Explanatory panel (dev) / generic “sign-in required” text; no API call is fired |
| Loading | Every query | Skeleton blocks, `aria-busy`, controls disabled |
| Empty | Diagnoses / medications | Localised “nothing recorded yet” + primary add action |
| Validation `400` | Forms | Field errors + form-level summary; focus moves to the first invalid field |
| `401` | Any call | “Session expired / token invalid” panel, offer token re-entry (dev), no redirect loop |
| `403` | Any call | “You do not have access to this record” — no retry storm |
| `404` | Detail | “Visit not found in your workspace” + back link |
| `409` | Create visit | “This appointment is already linked to another visit” |
| Network failure | Any call | Localised retry action; TanStack Query retry stays at the shared default (1) |
| Success | Mutations | Toast + inline confirmation; data refreshed from the invalidated query |
| Delete pending | Medication | Dialog stays open, destructive button disabled until `204` |

Every message is a translation key; no raw status codes or EF/property names are shown to the user.

## 11. Accessibility

- Every control has a persistent visible `<label>`; placeholders are never the only label.
- Errors are linked with `aria-describedby` and marked `aria-invalid`; the error container uses
  `role="alert"`.
- Save/delete results are announced (`aria-live="polite"` for success, `role="alert"` for errors).
- The delete dialog is a real dialog with an accessible name, initial focus on the safe action,
  `Esc` to cancel, and focus returned to the trigger.
- Sections use landmarks and headings in order (`h1` page, `h2` sections, `h3` items).
- Focus rings use the existing theme tokens and stay visible in both themes and both directions.
- Icon-only buttons carry translated `aria-label`s; icons are `aria-hidden`.

- New namespace `MedicalRecords` added to **both** `src/messages/en.json` and

- Arabic copy is reviewed for medical terminology (“زيارة طبية”, “تشخيص”, “وصفة/دواء”).
- No user-facing string literals in components; ESLint cannot catch this, so it is a review item.

## 18. Risks and known limitations

|---|---|---|
| 1 | **No login endpoint** (D-16), so the UI needs D-28 | The bridge is dev-only, `sessionStorage`, masked; real auth stays out of scope and is recorded as such |

| 8 | Hard delete (D-23) is irreversible | Explicit warning in the confirm dialog; no “undo” is promised |
| 9 | `ProblemDetails.errors` keys are PascalCase | `readFieldErrors` normalises keys; covered by review and M-7 |
