## Goal
Real server-side authentication: users log in with email/password or Google, register as Doctor or Secretary, verify their email, and recover their password; JWTs carry the claims the existing authorization needs, plus `DoctorId`; seed users exist for the demo.

## Business rules & security constraints
AGENTS.md §5 "Authentication" in full: role allow-list (`Doctor`, `Secretary`; never `Admin`), hashed passwords, hashed single-use expiring tokens, no account enumeration, inactive/unverified cannot log in (Q-11), no secrets or tokens in logs/repo, Firebase token validated on the server, role never taken from the client for Google users.

## Affected layers & files
Domain: identity/credential data, email-verification and password-reset token entities, enums. Application: auth services, `IEmailService`, token/JWT abstraction, Firebase token validator abstraction, DTOs, validators, mapping profile. Infrastructure: entity configurations, migration, JWT issuing, SMTP implementation, Firebase validator, seeder. Api: `AuthController`, authentication/authorization setup, Swagger. Config: `appsettings` options + user-secrets/env (SMTP, JWT key, Firebase project id).

## API contract (proposed — freeze in `plan`, share with F6-C2 and all members)
| Route | Request | Response |
|-------|---------|----------|
| `POST /api/auth/login` | email, password | accessToken, expiresAt, user (id, fullName, email, role, doctorId?) |
| `POST /api/auth/register` | fullName, email, password, phone?, role (`Doctor`/`Secretary`), specialization? | 201 + message to verify email |
| `POST /api/auth/verify-email` *(route proposed)* | token (and email if needed) | 204 |
| `POST /api/auth/resend-verification` *(proposed)* | email | 204 (same answer always) |
| `POST /api/auth/forgot-password` | email | 204 (same answer always) |
| `POST /api/auth/reset-password` | token, newPassword (+email if needed) | 204 |
| `POST /api/auth/google` | idToken | same as login |
Errors: 400 validation, 401 invalid credentials/token, 403 inactive/unverified, 409 email already exists.

## Acceptance criteria
- [x] Seeded Admin, Doctor, Secretary can log in; token contains the agreed claims and `DoctorId` for doctors; existing Phase 1 authorization works with real tokens.
- [x] Register creates the right profile; `Admin` role is rejected; duplicate email → 409.
- [x] Unverified or inactive account cannot log in (per Q-11).
- [x] Verification and reset tokens are hashed, expire, are single-use; forgot-password/resend never reveal whether an email exists.
- [x] Invalid/forged/expired Firebase token → 401; Google users never receive a client-chosen role.
- [x] No password, token, or secret appears in logs, responses, or the repository.
