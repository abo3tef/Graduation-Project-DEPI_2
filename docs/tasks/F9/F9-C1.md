# F9-C1 — Vital Signs: Backend

- Feature: F9 — Vital Signs & Visit Enhancements   - Owner: Anton   - Branch: `feature/anton-vitals`   - Phase: Phase 2
- Status: Approved
- Depends on: F6-C1 checkpoint A, Phase 1 visit entity

## Goal
Record, list, and edit vital signs linked to a medical visit by the owning doctor.

## Source requirements
FR-26, FR-27, FR-14; BR-09; BRULE-05, BRULE-06, BRULE-08; Class Spec §4.8 (`VitalSigns`: blood pressure, heart rate, temperature, respiratory rate, weight, height, SpO2; MedicalVisit records VitalSigns 1:M).

## Business rules & security constraints
Only the owning doctor creates/edits; secretary has no access (BRULE-10); the visit id in the route determines the patient — never accept a patient id from the client; values validated against ranges approved in Q-19; all fields optional unless the team requires otherwise; no delete in this Cycle.

## Affected layers & files
Domain: `VitalSigns` entity (verify existence) + methods. Application: vital-signs service, DTOs, validators, mapping profile (no `VisitId`/ownership from input). Infrastructure: `VitalSignsConfiguration` (precision for temperature/weight/height, FK to visit, delete behavior without cascade over history), migration. Api: actions under the medical-visits controller.

## API contract (proposed)
`POST /api/medical-visits/{visitId}/vital-signs` · `GET /api/medical-visits/{visitId}/vital-signs` · `PUT /api/medical-visits/{visitId}/vital-signs/{vitalSignsId}`. Visit detail response includes the visit's vital signs (coordinate with F3/F4 DTOs).
